## 摘要
现代LLM智能体在持久化工作空间中运行，其累积历史可能超过GPU KV容量和模型原生上下文窗口。现有系统通常将较旧的上下文压缩为摘要或稍后以文本形式检索，要么丢失细粒度的执行证据，要么反复预填充模型已处理的内容。我们提出了KVMem，一种KV上下文虚拟化系统，将溢出的工作空间历史以分页KV状态的形式跨GPU内存、主机内存和NVMe进行保存。KVMem使用轻量级、模型原生的注意力空间索引来选择相关历史块，并物化一个受模型原生上下文窗口限制的、依赖查询的执行视图。在长达一百万Token历史的长上下文智能体基准上的广泛评估，包括LongMemEval、MemoryAgentBench和AgentLongBench，表明KVMem通常比基于压缩的方法（处理上下文溢出的事实标准）实现更高的任务效用和更高的推理效率。在使用Qwen3.8-27B的DeepSWE长上下文测试中，KVMem将任务成功率从仅压缩上下文管理的43.8%提高到48.4%。在我们的本地部署评估中，KVMem在配备24 GB RTX 5090笔记本GPU的现成笔记本电脑上，使用MTP运行Qwen3.6/3.8-27B NVFP4，虚拟化高达100万Token的智能体工作空间——是模型原生256K Token上下文窗口的四倍。在单会话设置中，KVMem生成约50 Token/s，为本地智能体执行提供交互式响应。更广泛地说，通过将可寻址工作空间大小与LLM的原生上下文窗口解耦，KVMem为工作空间可增长超过该窗口的长期运行智能体提供了一条实用路径。

## Abstract
Modern LLM agents operate in persistent workspaces whose accumulated history can exceed both GPU KV capacity and the model's native context window. Existing systems typically compact older context into summaries or retrieve it later as text, either losing fine-grained execution evidence or repeatedly prefilling content that the model has already processed. We present KVMem, a KV-context virtualization system that preserves overflowed workspace history as paged KV state across GPU memory, host memory, and NVMe. KVMem uses lightweight, model-native attention-space indexes to select relevant historical blocks and materializes a query-dependent execution view bounded by the model's native context window. Extensive evaluations on long-context agent benchmarks spanning histories up to one million tokens, including LongMemEval, MemoryAgentBench, and AgentLongBench, show that KVMem generally achieves higher task utility and greater inference efficiency than compaction-based approaches, the de facto standard for handling context overflow. In the DeepSWE long-context test with Qwen3.8-27B, KVMem improves task success from 43.8% with compaction-only context management to 48.4%.   In our local-deployment evaluation, KVMem runs Qwen3.6/3.8-27B NVFP4 with MTP on an off-the-shelf laptop equipped with a 24\,GB RTX 5090 Laptop GPU, virtualizing agent workspaces of up to 1M tokens-four times the model's native 256K-token context window. In a single-session setting, KVMem generates $\sim$50 tokens/s, providing interactive responsiveness for local agent execution. More broadly, by decoupling addressable workspace size from the LLM's native context window, KVMem provides a practical path toward long-running agents whose workspaces can grow beyond that window.

## 1. 论文核心问题与整体含义（研究动机与背景）

- **背景**：现代 LLM 智能体（agent）往往运行在“持久化工作空间”中，例如项目目录、代码工作树、笔记本目录等。这些工作空间不仅包含对话历史，还包含工具调用输出、文件内容、编辑记录、中间结果、任务约束等，随着任务推进不断累积，形成远超单次对话的模型相关上下文。
- **双重执行瓶颈**：
  1. **GPU 内存限制**：即使历史总长度未超过模型原生上下文窗口，KV cache 与模型权重、运行时缓冲、推测解码状态等共享有限的 GPU 显存，导致单个会话实际可用的上下文窗口显著小于模型宣称的最大值。
  2. **原生窗口限制**：长期执行时工作区历史本身可增长到超过模型原生上下文窗口（例如 Qwen3.6-27B 原生 256K tokens，而长上下文 agent 基准的历史可达几十万到数百万 tokens）。
- **现有方法的缺陷**：
  - **Compaction（压缩）**：把较旧历史压缩为摘要，属于有损压缩。在压缩时无法预知未来哪些细节会变成关键信息，容易丢失早期文件中某一个句子、工具输出中的某个值、或用户约束等关键细粒度证据。
  - **文本检索（Text Retrieval）**：将历史以文本形式存储在外部，需要时再检索插入 prompt。这虽然可以找回部分被压缩遗漏的内容，但检索到的文本必须重新进行 prefill（尽管这些 token 之前已被模型处理过），造成大量重复计算和时延。
- **核心洞察**：当历史上下文离开活跃执行窗口时，模型其实已经把它编码为 KV 状态；唯一不确定的是未来哪个子集会被重新需要。借鉴虚拟内存思路，可以把“可寻址工作空间大小”与“GPU 上物理驻留的 KV 状态大小”解耦，将溢出的历史以分页 KV 状态保存在于更大的后备存储上，按需选择并物化相关部分。
- **KVMem 的定位**：一个 KV 上下文虚拟化系统，让 agent 访问远超其活跃上下文与 GPU KV 容量的工作空间，同时避免每次回忆历史都重新进行文本 prefill。论文认为累积的 agent 上下文是一种可虚拟化的系统资源，需要区分“可寻址工作空间”“模型可见执行窗口”和“GPU 驻留 KV 集合”三个概念。

## 2. 方法论：核心思想、关键技术细节、公式与流程

### 2.1 总体架构

KVMem 将已处理的工作区历史保存为分页 KV 块（logical blocks），跨 GPU 内存、主机内存（host memory）和 NVMe 存储分层放置。每个智能体步骤（agent step）开始时，KVMem 依据当前查询（query）从持久化的 KV 仓库中检索一小部分相关历史块，并按时间顺序、位置一致地组装成一个有界的执行视图（execution view），该视图不超过模型原生上下文窗口与 GPU KV 预算。

### 2.2 问题建模与容量约束

- 历史 KV 被划分为大小为 `B_blk` 的逻辑块：`B_t = {b1, b2, ..., b_Mt}`。
- 三个容量界限：
  - `B_model`：模型原生上下文窗口大小；
  - `B_gpu`：GPU 显存允许的最大 token 等效 KV 状态；
  - `B_m`：后备工作空间（host memory + NVMe）可以容纳的 token 等效 KV 状态。
- 活跃上下文预算为 `B_a = min(B_model, B_gpu)`。
- 给定策略 π，在召回点 τ 选择历史工作集 `R_πτ`，强制执行 `N(Q_τ) + B_blk |R_πτ| ≤ B_a`（其中 `Q_τ` 是必选上下文），优化目标：最大化 Fidelity(π)，最小化 RecoveryCost(π)。

### 2.3 三大设计挑战与对应机制

#### 挑战 1：何时召回 → 步级内存调度（Step-Level Memory Scheduling）

- 观察：作者分析了 OpenHands SWE-bench Lite 的 8 条 rollout，用相邻 128-token 滑动窗口（stride 32）测量历史注意力的 KL 散度。同一 agent 步骤内相邻窗口 KL 平均仅 0.070 bits，而跨越步骤边界的窗口 KL 平均 2.59 bits（高 37.3 倍）。
- 结论：历史相关性在 agent 步骤内部变化缓慢，在步骤边界发生剧烈变化。
- 因此 KVMem 采用“步级内存调度”：每个 agent 步骤更新一次历史工作集，更新时机在**当前 step 的 prefill 之后、decode 之前**。Prefill 期间收集查询信号，decode 期间固定该工作集，新生成 KV 增长在其尾部。下一个 agent 调用开始新的召回周期。

#### 挑战 2：召回什么 → 查询条件化 KV 检索（Query-Conditioned KV Retrieval）

- 动机：百万 token 级别的历史 KV 无法逐 token 扫描或存储全量索引。历史注意力高度稀疏：平均每个窗口覆盖 103.1 个历史块，top-8 块就集中了 66.5% 的历史注意力质量，top-16 则达 77.0%。
- **Mean-K 索引构造**：对每个历史块，在每个层、每个 KV head 上计算其去 RoPE 后的 K 向量的均值（position-independent Mean-K）：
  `\bar{k}_{l,b,g} = (1/|b|) ∑_{i∈b} \tilde{k}_{l,i,g}`
  - 每个块只保留每层每头一个 K 向量，索引占用量远小于完整 KV，也支持更细粒度（默认块大小 32 tokens）。
- **查询条件化块打分**：将当前查询的 Q 向量去除 RoPE 后与所有候选块的 Mean-K 做缩放点积，再经过跨候选块的 softmax 归一化：
  `R_b = ∑_m mean_{l,h} softmax_{b′∈C}( (q_{l,m,h}^⊤ \bar{k}_{l,b′,g(h)})/√d )_b`
  - 得分越高的块越可能被选中；默认保留 sink 和 recent 块，其余按得分从高到低填满活跃预算，再按时间顺序恢复。
- 可扩展性：完整 Mean-K 索引放在主机内存中，GPU 上仅通过有界 tile 分块评分，评分时可全局 softmax 跨 tile 归一化，保证与一次完整评分等价。

#### 挑战 3：如何召回 → 分层 KV 管理与高质量恢复（Tiered KV Management）

- **仓库视图 vs 执行视图**：仓库视图追踪每个块的物理位置（GPU 页池/主机内存/NVMe），执行视图表示当前选中、按时间顺序编号、分配连续紧凑逻辑位置的 KV 集合。
- 物理页通过页表（page table）映射到逻辑顺序，不需要拷贝到密集缓存；但 RoPE 编码的 K 只有在编码时的位置才有效。为此 KVMem 以“原始 K（position-independent raw K）+ 重新应用 RoPE”为可靠恢复机制；V 可直接复制。
- **优化措施**：
  1. **Proactive Stage-Out（主动迁出）**：在 prefill chunk n 完成之后、chunk n+1 计算期间，异步为已完成块在主机内存创建副本；必要时再异步落到 NVMe。这样下一次工作集切换时，出界的块已有有效低层副本，GPU 页可立即回收。
  2. **Retrieval-Aware Hierarchical Reuse（检索感知的分层复用）**：
     - 重叠块复用 GPU 页：将工作集切换分解为 retained/ incoming/ outgoing 集合（W_t−1∩W_t、W_t\W_t−1、W_t−1\W_t），仅对物理缺失的块执行 stage-in；
     - 主机内存缓存策略综合考虑近期检索与累计检索频率，避免频繁召回块被 LRU 误逐出到 NVMe；
     - 限制 K 的原地 delta re-RoPE 次数，达到阈值后从 raw K 重新编码，避免低精度浮点累积误差。
  3. **Packed and Pipelined Rematerialization（打包与流水线化重建）**：
     - 将多个不连续块聚集到连续的主机 pinned-memory 缓冲区，打包后以大批量 H2D 传输到 GPU 暂存缓冲；
     - GPU 内核将 K 散射至目标 KV 页并应用新位置 RoPE，V 无需变换；
     - 三阶段流水线：CPU 聚集（batch n+1）→ H2D 传输（batch n）→ GPU 散射/重 RoPE（batch n−1），通过双缓冲和 CUDA events 避免设备范围同步。

### 2.4 执行流程（每步生命周期）

1. 新 agent step 开始 → 对当前输入做 chunked prefill；
2. Prefill 期间收集去 RoPE 的 Q 向量以及新完成块的 Mean-K 索引（同步更新到主机）；
3. Prefill 完成后，进行一次工作集更新：对历史块打分、选择、从仓库（GPU 或低层存储）取回；
4. 组装紧凑执行视图：通过页表映射物理页，对 K 做 re-RoPE 使其匹配新逻辑位置，加载一个 checkpoint 再对当前查询重新执行 prefill（避免重放整个早期上下文）；
5. 保持该历史工作集固定，进行 decode，直到该 agent 步结束。

### 2.5 工程实现（QW3 推理引擎）

- 由于现有服务系统（vLLM、SGLang、LMCache 等）未暴露所需端到端控制接口（模型执行、KV 页分配、RoPE、存储传输），作者从头实现了 C++/CUDA 推理引擎 **QW3**，支持连续批处理、前缀复用、多 token 预测（MTP）。
- 逻辑块大小与物理 KV 页对齐；每个块记录 ID、原始 token 范围、驻留层、低层位置、baked position（当前 K 中的 RoPE 帧）。
- 检索索引采用主机驻留、GPU 分块评分的做法，保持 GPU 内存占用量与索引大小无关；实现增量索引更新、重叠数据移动、免拷贝执行视图组装。

### 3.3 对比方法

- **Full Context**：完整历史保持在活跃上下文中（参考上界，仅当历史不超过模型原生 256K 窗口时报告）。

- **Compact-only**：把溢出的历史压缩为文本摘要（compaction 工作流）。
- **Compact+RAG**：额外从外置文本存储检索相关历史片段并插入 prompt（文本记忆系统模式）。
- **KVMem**：本文方法。

所有方法均在同一 QW3 后端和模型配置下执行，仅上下文管理策略不同，使用相同的活跃执行视图预算以保证公平（预算视工作区规模设定：LongMemEval-S 与 ≤256K 的 AgentLongBench 用 32K；MemoryAgentBench >256K 与 512K 的 AgentLongBench 用 64K；1M 的 AgentLongBench 用 100K）。

- **效率细粒度分析**：对 LongMemEval-S 报告了总计输入、fresh prefill、pre-answer latency。
- **消费级设备评测**：对比 vLLM、llama.cpp、KVMem 在 RTX 5090 Laptop 上的最大上下文/工作空间与生成速度。
- **服务端可扩展性实验**：固定 64K 执行视图，工作空间从 256K 增长到 10M tokens，观测 GPU/主机/NVMe 占用、检索延迟、TTFT、prefill/decode 吞吐。
- **DeepSWE 长程端到端评测**：前 16 任务 ×4 seeds = 64 rollout / 策略；共 128 rollout。
- 没有额外的消融研究（例如对不同块大小、不同召回频率、索引类型与 full-attention 对比等）。
- 实验对比覆盖了 3 个控制基准 + 1 个真实长程 agent 场景，方法数量、历史长度范围与硬件场景相对丰富，足以支撑主要结论。

### 5.2 实验是否充分、客观、公平？

- **优点**：
  - 对比方法统一使用同一推理引擎（QW3）和同一模型配置，仅上下文策略不同，控制了后端变量；
  - 在相同的 active-context 预算下比较 Sliding Window/Compact-only/Compact+RAG/KVMem，较公平；
  - DeepSWE 实验选择前 16 个任务（未按难度过滤）并重复 4 次采样，相对客观；
  - 报告了 DeepSWE 公开高质量模型结果作为参考，增强可信度。
- **不足**：
  - 没有报告 KVMem 自身的消融实验，读者无法判断每种机制（调度时机、Mean-K 索引、分层复用、打包流水线）分别贡献多少；
  - 没有与“全文重放（直接重复 prefill overflowed history）”做基线对比，难以单独量化 KV 复用的收益；
  - LongMemEval-S 中 KVMem 85.6% vs Compact+RAG 86.2%，差异很小，作者未做统计显著性检验；
  - DeepSWE 的公开模型对比使用的 agent harness 不同（mini-swe-agent vs Claude Code），作者已说明不能作为严格模型对比；
  - 消费级设备实验仅一个会话、少数代表性性能值（~50 tokens/s），没有详细跟踪资源变化；
  - 10M workspace 实验只使用 16 次冻结查询后的中位数，样本量较有限。

## 6. 主要结论与发现

- **任务效用**：KVMem 在三个长期历史基准上普遍优于 Sliding Window 与 Compact-only；与 Compact+RAG 相比基本相当或更优。
  - LongMemEval-S 上 KVMem 准确率 85.6%，接近 Full Context 的 86.6%（差 1.0 个百分点），远高于 Compact-only 的 45.6%；
  - AgentLongBench（≤256K）上 KVMem 成功率达 60.87%，略高于 Full Context 的 59.54%，说明有界的相关历史召回甚至可能缓解长上下文退化效应；
  - 超过 256K 原生窗口后，MemoryAgentBench(>256K) 上 KVMem 得分 40.99%，显著高于 Compact+RAG（34.80%）；AgentLongBench 1M 时 KVMem 50.0%，高于 Compact+RAG（42.0%）8 个百分点。
- **推理效率**：相比 Compact+RAG，KVMem 在除去摘要生成时间后仍把恢复时延降低 11.4–53.8 倍。
