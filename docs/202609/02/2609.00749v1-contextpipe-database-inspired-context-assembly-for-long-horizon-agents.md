## 摘要
长时程大语言模型（LLM）智能体需要上下文组装：运行时必须在硬性的上下文窗口预算和字节敏感的提示缓存下，决定每个提示中包含哪些内容、顺序如何，以及何时压缩历史记录。在生产级智能体系统中，这一逻辑分散在提示构建器、临时压缩例程、缓存破坏的规避方案以及各提供商的适配层中。我们认为，上下文组装在结构上与关系数据库中的查询执行同构：两者都在硬预算下执行，利用分级缓存，并借助统计信息。我们在ContextPipe中采用这一原则：一个五阶段流水线（计划-绑定-优化-执行-反馈），由结构化数据源目录、确定性缓存感知优化器和EXPLAIN ANALYZE跟踪提供支持。我们证明，ContextPipe中的上下文是可审计、可重放且故障隔离的。使用SWE-bench Pro Qutebrowser子集的初步评估表明，与仅追加的上下文构建策略相比，ContextPipe将总token量减少了31%，LLM调用减少了23%，响应时间减少了9%，但代价是KV缓存命中率较低。

## Abstract
Long-horizon large language model (LLM) agents require context assembly: the runtime must decide what to include in each prompt, in what order, and when to compact history under a hard context-window budget and a byte-sensitive prompt cache. In production agentic systems, this logic is scattered across prompt builders, ad hoc compaction routines, cache-break workarounds, and per-provider shims. We argue that context assembly is structurally isomorphic to query execution in a relational database: both execute under a hard budget, exploit a tiered cache, and leverage statistics. We adopt this discipline in ContextPipe: a five-phase pipeline (Plan Bind Optimize Execute Feedback) backed by a structured data-source catalog, a deterministic cache-aware optimizer, and an EXPLAIN ANALYZE trace. We show that context in ContextPipe is auditable, replayable, and failure-isolated. A preliminary evaluation using the SWE-bench Pro Qutebrowser subset shows that, compared with the append-only context construction policy, ContextPipe reduces total token volume by 31%, LLM calls by 23%, and response time by 9%, at the cost of a lower KV cache-hit ratio.

## 2. 论文提出的方法论：核心思想、关键技术细节、公式或算法流程

### 核心思想
- 将 **LLM 上下文组装**类比为 **关系数据库的查询执行**，具体映射关系为：
  - 声明式意图 ↔ 用户输入消息；
  - 隐式目录 ↔ 数据源的目录（生命周期分层、成本等）；
  - 硬资源限制 ↔ 上下文窗口；
  - 分级缓存 ↔ 提示词前缀缓存（prompt prefix cache）；
  - 统计信息 ↔ 历史 token 用量、缓存命中率、响应长度分位数；
  - 优化器 ↔ 顺序、压缩、缓存标记的确定性策略。
- 由此设计 ContextPipe：一个五阶段流水线，所有 LLM 调用（包括工具运行、子任务、压缩等）都必须经由此路径。

### 五阶段流水线（Plan → Bind → Optimize → Execute → Feedback）
1. **Plan（计划）**：纯函数，只读目录与统计信息。计算“上下文压力”（context pressure）：
   - \( P_{raw} = T_{used}/L_{eff} \)
   - \( P_{pred} = (T_{used} + R_o + R_t + R_s)/L_{eff} \)  
     其中 \( T_{used} \) 是当前已使用 token，\( L_{eff} \) 是有效输入上限，\( R_o\)（响应预留）、\( R_t\)（思考预留）、\( R_s\)（工具 schema 增长预留）是类型化预留量。
   - 预留量 \( R_o \) 按不同“（模型，查询来源）”桶的历史完成长度的分位数（稳态 p75、恢复期 p95）来估计，相当于数据库中的直方图基数估计。
   - 根据 \( P_{pred} \) 选择压缩层级（Normal / TrimSchemas / CompactHistory / AggressivePrune）。采用“只升不降”的 gating 规则，避免振荡；出现 recovery 状态（如 prompt too long）时进一步升级层级。

2. **Bind（绑定）**：唯一会执行外部 I/O 的阶段，并行获取计划中每个 section 的实际内容（记忆、历史、工具 schema、技能、emergent context 等），产出类型化工件（typed artifacts）而非字符串。

3. **Optimize（优化）**：基于确定性缓存感知策略，对绑定后的内容进行排序、压缩和溢出处理，输出可序列化请求和 trace。其实质是解决一个“带预算的放置/保留问题”（预算约束下的保留效用最大化 + 缓存敏感性），但作者明确指出该问题是 NP-hard 的前序约束背包问题，因此采用固定可判定策略：**按波动性递增排序、分层门控压缩、溢出**。优化器受 OptimizeLimits 的限制，任何被阻止的操作都会被记录为 SkippedOptimization trace。

4. **Execute（执行）**：负责将优化后的请求序列化并调用模型。支持 EXPLAIN-only 模式（不实际发送请求只返回 trace）。分离 Execute 与 Optimize 是为了让用户可以在无副作用的情况下查看“将要发送什么”。

5. **Feedback（反馈）**：记录实际结果（输入 token、缓存读取、缓存创建、输出 token、是否截断、缓存破裂的原因），写入 PipelineStats，供下一轮 Plan 使用。PipelineStats 是唯一在轮次内可被新写入的共享对象。

### 关键算法与策略
- **缓存感知有序放置**：将可重排 section 按 cache scope 波动性升序（Global < Session < None）排序，Identity 和 Constraints 作为锚点固定在最前。只有移动次数 ≤ max_reorder_moves 时才采纳新顺序，否则跳过并记录日志。缓存标记（cache marker）放在 scope 的边界处；若某些 volatile 值翻转，会抑制 None 标记；标记数量受 ProviderCachePolicy 的 Mmax 限制。
- **分层压缩**：
  - Normal：不压缩；
  - TrimSchemas：裁剪掉本轮不太可能用到的工具 schema；
  - CompactHistory：清除最早的工具结果并放置占位符，超限的大结果执行溢出（spill）到外部后端；
  - AggressivePrune：额外丢弃最旧的完整对话轮次，丢弃比例随压力上升，最低保留 4 轮。系统消息永不丢弃。
- **Spill（溢出）**：≥10,000 token 的 section（且存在后端、非 Identity/Constraints/Working Memory）被持久化到外部存储，并在请求内放置轻量 SpillReference。后端恢复失败时采用 fail-open 策略，替换占位符并记录 trace。
- **确定性启发式（Algorithm 1）**：Order → Compact → Spill → Mark → Serialize，所有步骤无随机性，结果可复现。
- **性质保证**：通过构造证明了四个性质（Lemma 1锚点/顺序、Lemma 2保护、Lemma 3配对/恢复性，以及 Property 1审计完备性、Property 2回放确定性、Property 3故障隔离）——这些被作者称为“可作为实现测试规范的属性”，而非严格的数学定理。

### 新型目录和跨轮机制
- **ContextSources 目录**：将数据源按生命周期分为 8 个层级（tier），包括 System、AgentSchemas、SessionLatches、SessionStatic、SessionState、PerTurn、Emergent、Feedback。每个数据源登记 schema（tier、kind、scope、priority、est tokens、bind latency等）。
- **SessionLatches（会话闩锁）**：延迟求值、首次触发后冻结的会话级值（例如 beta headers、cache scope、provider feature flags），防止中途更改破坏缓存前缀。将其提升为一等目录层级。
- **EmergentContext（涌现上下文）**：在 Plan 之后、由工具执行或异步发现的新上下文（如技能触发、工具摘要、预取的记忆），在当轮结束排队、下一轮 Bind 时消费。带安全三件套：每个 TTL（仅下一轮）、内容哈希去重、列表容量上限。
- **ForkPrefix**：多智能体场景下的缓存前缀共享——父代理在 spawn 子代理时冻结父级缓存前缀的规范字节快照，供子代理第一轮使用，同时包含 per-tool 的规范和 SHA-256 哈希，用于后续缓存破裂归因。当前实现中，默认执行器还没有完全将快照接入子代理的第一个 Bind 阶段，作者对此有坦诚说明。

### 统计子系统
- PipelineStats 针对每个“（model, query_source)”维护一个 PercentileDigest（上限 512 个样本的有序列表，满员时删除中位数），用于估计响应预留量；用 EMA 跟踪缓存命中率（λ=0.1）和每个 section 的 token 用量（α=0.3）；每类 section 有指纹和 churn counter；缓存破裂与压缩事件存入 64 条环形缓冲；连续压缩级联会触发 alert。
- 失败轮次只记录失败，不写入使用量样本，避免污染分位数字典。

### 阴影管道（Shadow-pipeline rollout）
- 新配置先在 shadow 模式下并行运行但不发请求，由 diff checker 对比系统块哈希、工具 schema 哈希、消息计数/角色序列、缓存标记位置和 token 估算，条件满足后逐步上线（shadow → shadow-verified → flip → retire）。

## 6. 论文的主要结论与发现

- **结论 1**：数据库启发式架构可以用于上下文组装。ContextPipe 将散落的上下文逻辑统一为五阶段流水线和目录，使 LLM 提示组装具备可审计、可回放、故障隔离等运维属性。
- **结论 2（定量结果）**：相比 Flat 基线，Structured 策略：
  - 总 token 量显著降低：**减少 31.1%**；
  - 重复缓存读取（cached tokens）降低：**39%**；
  - LLM 调用次数降低：**23.1%**；
  - 响应时间降低：**8.7%**；
  - 完成 token 降低：**23.5%**。
  - 这些收益以**缓存命中率降低 9.1 个百分点**为代价（95.3% → 86.2%），未缓存（fresh）token 量增加了一倍以上（46,581 → 99,967）。
- **结论 3（成本模型）**：当缓存 token 价格低于 fresh token 的 14.5% 时（如 DeepSeek r ≈ 0.1），Flat 在计费上更便宜；而缓存价格≥14.5% fresh 价格时 Structured 更划算（文中示例 r=0.25 时 Structured 降低约 13% 计费成本）。因此 Structured 的优势主要集中在：减少上下文总量、调用次数、响应时间、保留更多窗口余量，而不是无条件降低账单。
- **结论 4（可诊断性）**：trace 能精确定位每一次缓存破裂的起因（压缩、schema 剪枝、层级变化），压缩层级的一次变化会带来一回合的缓存破裂，随后下一轮恢复高命中率。这让运维可以区分“必要成本”与“异常退化”。

## 7. 优点：方法或实验设计上的亮点

- **类比精准、系统性强**：将上下文组装问题完整映射到数据库优化体系（目录、压力/基数估计、计划、执行、反馈、EXPLAIN），为看似纠缠不清的 agent 状态管理引入结构化工程方法。
- **确定性+可审计机制**：Optimizer 是一个无随机性的有界启发式，每一决定无论应用与否都进入 trace。这为调试、回归测试、故障后重放提供坚实基础。
- **多阶段的纯度契约**：Plan 为纯函数、Bind 唯一 I/O、Execute 唯一模型调用、Feedback 唯一状态写入者。各阶段状态隔离，可单元测试。
- **良好的故障语义**：溢出失败 degrade 为占位符；Execute 失败不污染统计样本；紧耦合的边界验证捕获“优化器决策被下游忽略”的危险问题。
- **显式的成本建模与权衡讨论**：使用 E(r)=fresh+r·cached 的分解，并对缓存价格比做了盈亏平衡分析，不回避优化带来的缓存命中率下降。
- **组织完备性的提升**：将 SessionLatches 和 EmergentContext 建模成一等目录类别，揭示并修复了现有系统中隐匿的脆弱点（如 beta header 变化导致缓存破裂、跨轮上下文重复注入）。
- **有先进的多智能体缓存方案设计意图**：ForkPrefix 提供父子 agent 的缓存共享思路，即使尚未完全接入，也是一种新颖且有价值的方向。

## 8. 不足与局限：包括实验覆盖、偏差风险、应用限制等

- **实验覆盖严重不足**：
  - 只用了 SWE-bench Pro Qutebrowser 中的 3/79 实例，样本过小，结果可能受到个别实例特性支配；
  - 没有报告 resolve rate（质量指标）具体数值，只有“探索性质量持平”的说法；
  - 没有跨模型、跨任务类型、跨代码仓库的验证，结论的普适性未建立。
- **消融缺失**：A1–A4 计划内消融尚未执行，无法确定哪些组件贡献了主要效果；尤其在只报告宏观指标、不拆分机制效果的情况下，机制归因不充分。
- **建模简化**：优化器回避了理论上的 NP-hard 优化，使用固定顺序（sorts）和分层门控启发式，其最优性或接近程度没有理论分析或与搜索方法的对比；优化效果可能高度依赖 section 数量少、类型固定的 agentic 设定。
- **缓存命中率下降的代价被低估的风险**：文中所用 provider-normalized缓存指标不可跨厂商直接换算；真实计费取决于供应商的缓存折扣、最低缓存长度等因素，评估中未涉及实际 vendor 定价的差异对比。
- **实现成熟度问题**：
  - ForkPrefix 在默认执行器中尚未完全接线（“not yet wired”），只提供设计上的属性论证；
  - 只实现了部分统计量（Rt、Rs 默认 0，只有 Ro 被实现），说明机制的完整版并未完全落地。
- **技术与架构限制**：系统假设上下文所有来源都可被编入固定目录；对于不可控、不可预计的第三方工具结果或频繁变化的模板，本方法的可预测性降低；外部 spill 后端的存在又增加了新的运维依赖和失效概率；溢出重取失败时，无论 “fail-open”还是“记录占位符”，仍会造成上下文缺失。
- **实验基础设施信息缺失**：未报告 GPU/推理服务等说明，复现成本难以估算。
- **发表形式可能是 workshop 论文**：VLDB 2026 Workshop 论文篇幅和性质决定了其结论为“初步(preliminary)”，仍需在完整长文或后续工作中扩展。
