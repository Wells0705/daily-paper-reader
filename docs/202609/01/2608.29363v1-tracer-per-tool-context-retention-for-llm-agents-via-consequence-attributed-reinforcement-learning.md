## 摘要
企业数据智能体通过多个推理步骤串联大量工具调用来回答业务查询，通常每次会话会累积数十万个上下文令牌。现有的压缩策略通常分配保留预算时，不考虑移除单个工具输出所带来的下游后果。因此，激进的压缩可能会触发代价高昂的工具重新调用，从而抵消最初的节省。我们将这一现象称为“压缩-后果差距”。为缩小这一差距，我们提出了TRACER，它将压缩建模为一个序列化的逐工具决策问题。一个轻量级的REINFORCE策略仅利用每次压缩事件时可用的信息，来分配查询条件下的保留比率。其后果感知目标共同考量任务成功率、总令牌消耗以及压缩后的工具重新调用。为了改进信用分配，TRACER使用一个学习到的结果模型，将所选保留比率的预测后果与完全保留每个工具输出的预测后果进行比较。在三个压缩器后端的保留生产查询上，与保留全部上下文相比，TRACER将总令牌消耗降低了29%-46%，同时保持相当或更高的任务成功率。与基于工具类型的静态策略相比，TRACER额外节省了15%-18%的令牌。干预式推演表明，学习到的逐工具信用分数与测量的单工具后果相关。学习到的策略在跨智能体主干和压缩器架构迁移时也能产生正向节省，并在五个保留的LOCA-bench环境上将令牌消耗降低了18%-25%。这些结果证明了后果感知的逐工具上下文保留对于提高长周期语言智能体效率的价值。

## Abstract
Enterprise data agents answer business queries by chaining many tool calls over multiple reasoning steps, routinely accumulating hundreds of thousands of context tokens per session. Existing compression strategies typically allocate retention budgets without accounting for the downstream consequences of removing individual tool outputs. Aggressive compression may therefore trigger costly tool re-invocations that offset the initial savings. We call this the compression--consequence gap. To close it, we propose TRACER, which formulates compression as a sequential per-tool decision problem. A lightweight REINFORCE policy assigns query-conditioned retention ratios using only information available at each compression event. Its consequence-aware objective jointly accounts for task success, total token consumption, and post-compression tool re-invocations. To improve credit assignment, TRACER uses a learned outcome model to compare the predicted consequences of the selected retention ratio with those of fully retaining each tool output. On held-out production queries across three compressor backends, TRACER reduces total token consumption by 29--46% relative to keeping all context while maintaining comparable or higher task success. Compared with a tool-type-conditional static policy, TRACER provides an additional 15--18% of token savings. Interventional rollouts show that the learned per-tool credit scores correlate with measured single-tool consequences. The learned policy also yields positive savings when transferred across agent backbones and compressor architectures, and reduces token consumption by 18--25% on five held-out LOCA-bench environments. These results demonstrate the value of consequence-aware, per-tool context retention for improving the efficiency of long-horizon language agents.

## 2. 论文提出的方法论

### 2.1 总体框架

TRACER 将上下文压缩重定义为**序列化的逐工具决策问题**：

- 在一个完整会话中，每次上下文超过预算阈值时触发一次“压缩事件”；
- 在每个压缩事件，策略网络读取当前状态，为每个已存在的工具输出分配一个**保留比率 r ∈ [0.05, 1.0]**；
- 固定压缩器按这些比率对各个工具输出压缩后，智能体继续执行任务；
- 在会话结束后，依据任务成功、总token消耗和工具重调用次数构建奖励信号；
- 用 REINFORCE 训练策略，同时用一个**学习到的结果模型**（outcome model）做单工具反事实归因，以缓解奖励稀疏和信用分配困难。

### 2.2 关键公式与设计

- **会话级基础奖励**（仅终局获得）：  
  \[
  R_{base,k} = \mathbb{1}[k=T_c] \left( success - \lambda_{tok}\, clamp(T/T_{base}, 0.2, 2) \right)
  \]
  - `success ∈ {0,1}`；`T` 为会话总token数；`T_base` 为同查询下不压缩时五次参考运行的平均token数。

- **事件级重调用惩罚**（每个压缩事件后计算）：  
  \[
  P_{recall,t} = \lambda_{recall}\, clamp\left(\frac{N_{post,t} - N_{pre,t}}{N_{pre,t}}, 0, 2\right)
  \]
  - `N_post,t` 与 `N_pre,t` 分别表示压缩事件后与参考时间窗内的工具调用数。

- **总目标**：  
  \[
  J(\theta) = E_{\tau \sim \pi_\theta}\left[ R_{base} - \sum_t P_{recall,t}\right]
  \]

- **策略参数化**：动作是基于 **Beta 分布**采样的，  
  \[
  \tilde a_i \sim \mathrm{Beta}(\tilde m_i \kappa_0, (1-\tilde m_i)\kappa_0)
  \]
  - `\tilde m_i = σ(net_i)` 是网络预测的均值，`κ0=8` 固定集中度；
  - Beta分布天然匹配有界动作区间，无需截断；测试时采用确定性均值。
  - 策略网络是两层MLP，输入状态 `s∈R^174`，输出每个工具实例保留均值的16维向量（16个工具槽位按实例区分，同类型工具多次调用拥有独立槽位、独立比率和独立梯度）。

- **双通道信用分配机制**：
  1. **均匀惩罚下限**：将事件级重调用惩罚均匀分摊到当前活动工具上，保证即使归因模型失效，仍有粗略但正确的惩罚信号。
  2. **反事实归因**：用结果模型 `f_φ`（两层4头Transformer，输入为工具token + 查询token）预测逐工具重调用数 `n̂_i`、日志总token `T̂_log` 和成功概率 `p̂`，然后比较“当前保留比率”与“完全保留工具i”的预测代价差，得到逐工具归因信用：
     \[
     credit_i^{attr} = \lambda_{save}(1-r_i)\frac{tok_i}{T_{base}} - [\hat C(s,a) - \hat C(s,a; r_i:=1)]
     \]
     该信号**双向**：若压缩节省的token超过预测的下游成本，则鼓励压缩；若预测成本更高，则抑制压缩。

- **梯度更新**：  
  \[
  \mathcal L(\theta) = -\sum_{i \in active} coeff_i \log \pi_\theta(a_i|s)
  \]
  - 其中 `coeff_i = αA_t + credit_floor_i + β_t credit_i^{attr}`；
  - 前20个episode为warm-up（β=0），之后10个episode线性退火至β=1，此后每5个episode更新一次结果模型。

### 3.1 平台与数据

### 3.3 对比方法与评价指标

- **基线**：
  - Keep-all：保留全部上下文（成功率上限和token基线）；
  - Uniform-0.5：所有工具固定0.5的保留比率；
  - Recency：随时间线性衰减的保留比率；
  - Token-proportional：按输出大小反向惩罚；

- **迁移测试**：冻结在 Claude 上的策略，零样本用于 Qwen-3.7-Max 和 GPT-5.5；以及冻结在 Truncation 后端的策略零样本用于 AGORA 后端，对比在 AGORA 上重新训练的 TRACER。

## 6. 论文的主要结论与发现

- **压缩–后果差距是真实且显著的**：固定基线（Uniform/Recency/Token-prop）在 Truncation 和 Self-Info 上不仅不节省token，反而使总token消耗相比 keep-all 增加 3%–24%，原因正是压缩引起的工具重调用。
- **TRACER 有效降低总token并保持/提升成功率**：
  - 相比完全保留上下文，总token消耗降低 **29%–46%**（Truncation 31%、Summarization 46%、Self-Info 29%、AGORA 34%）；
  - 任务成功率与 keep-all 相当或更高；
  - 重调用率保持在 ≤0.025，说明“非以重调用换节省”。
- **逐工具查询条件化优于静态工具类型策略**：相比 Tool-type-conditional，TRACER 额外节省 15%–18% token；说明相同工具类型在不同查询下也有不同重要性。
- **归因模型贡献显著**：加归因的 TRACER 相比 RL-only，成功率提升 2.2–4.8个百分点，iso-success token比率额外下降 3.4%–4.7%，重调用率进一步降低。
- **结果模型预测具有方向可靠性**：预测与真实单工具干预代价差 Spearman ρ=0.66；可恢复82%的 top-3 高后果工具；84%的信用方向与真实rollout一致。
- **可迁移性强**：
  - 冻结策略在 GPT-5.5 和 Qwen-3.7-Max 上零样本仍节省 18%–40% token；
  - 从 Truncation 零样本转移到 AGORA 后端节省 31% token；在 AGORA 上直接训练后提升到 34%；
  - 在 LOCA-bench 5个留出环境上（三个长上下文窗口）节省 18%–25% token，且成功率高于 keep-all。

## 7. 优点

- **问题定义清晰且有实际价值**：将“压缩引发的重调用成本”形式化为可优化目标，抓住了长程agent上下文管理中常被忽视的关键痛点。
- **决策粒度高且可解释**：逐工具（甚至逐工具实例）分配保留比率，区别于token级或整个turn级策略，能更精细地匹配工具输出的下游效用。
- **后果感知奖励设计**：同时考虑任务成功、token效率、事件级重调用惩罚，从机制上避免“假节省”。
- **信用分配方案新颖**：用 Beta 策略 + REINFORCE，配合**学习到的结果模型做单工具反事实归因**，缓解了稀疏奖励下的信用分配问题；归因模型还通过真实干预rollout验证了可靠性。
- **泛化和迁移验证充分**：跨压缩器、跨骨干模型、跨生产环境与公共benchmark的试验，显著增强了结论的可信度。
- **部署成本可接受**：约102K参数、CPU可训练，训练成本可在3–6周内由生产流量中的token节省回本。

## 8. 不足与局限

- **生产数据不可公开复现**：核心实验使用私有电商智能体数据；论文附录也说明不提供完整轨迹、检查点和原始匹配输入，只能做“源码检查与语义级测试”，无法端到端精确复现。
- **环境与任务范围有限**：生产查询仅120条，LOCA-bench 并非广泛验证过的老牌基准；对更广泛工具集、更长会话（如50+步）和更复杂多智能体场景尚未验证。
- **结果模型近似性**：结果模型的 Spearman ρ=0.66、方向准确率84%，并非完美；训练奖励中的窗口式调用计数存在自然波动，论文仅提出“provenance upgrade”作为未来升级，并未在总结果中采用。
- **无正式因果保证**：论文承认归因模型并不提供形式化因果保证，其价值主要依赖经验验证（消融和干预rollout）。
- **外部API非确定性**：远程模型和生产后端的随机性无法完全控制，虽然使用随机种子复现了内部随机选择，但不能保证不同API版本/时间下的精确一致。
- **成本分析偏保守但仍有遗漏**：训练成本回收计算只计入输入token价格，未包含摘要模型调用、Self-Info评分器开销、输出token价格、CPU/服务器成本、重试、延迟、维护和分布漂移等。
- **策略可能随分布漂移退化**：固定策略在生产环境出现新型查询/工具输出分布时可能失效，部署需重新校准，论文未给出持续适应机制。
