## 摘要
多智能体大语言模型（LLM）工作流已成为通过专门化LLM智能体之间的协作推理来解决复杂、开放式任务的强大范式，但由于重复的LLM调用和长程上下文积累，它们会产生大量运营成本。现有的级联路由方法做出一次性、查询级别的决策，无法适应多步骤工作流的动态、状态依赖特性，在这些工作流中，每个步骤选择合适的LLM取决于不断变化的任务进度、剩余任务难度和成本效率要求。我们提出了ProgRouter，一种在线进度引导的路由框架，它在跨工作流步骤中自适应地选择LLM智能体，以在遵守时间和成本预算的同时保持任务解决质量。ProgRouter引入了一个多视图任务进度评分器，将粗略的工作流结果状态与子任务完成度、进度趋势和工作流状态质量的细粒度信号相结合。然后，一个双路径任务进度预测器和一个自适应元门控机制估计每个候选路由LLM的进度增益。ProgRouter做出在线逐步路由决策，平衡进度增益、任务时间预算和长期运营成本效率。在HumanEval Plus、MBPP、MATH-500和ASQA上的实验，涵盖智能体代码生成、数学推理和检索增强的长形式问答，表明ProgRouter在相对于关键基线降低运营成本的同时，保持了强大的任务解决性能。

## Abstract
Multi-agent large language model (LLM) workflows have emerged as a powerful paradigm for solving complex, open-ended tasks through collaborative reasoning among specialized LLM agents, but they incur substantial operating costs due to repeated LLM invocations and long-horizon context accumulation. Existing cascade routing methods make one-shot, query-level decisions and cannot adapt to the dynamic, state-dependent nature of multi-step workflows, in which the right LLM at each step depends on evolving task progress, remaining task difficulty, and cost-efficiency requirements. We present ProgRouter, an online progress-guided routing framework that adaptively selects LLM agents across workflow steps to preserve task-solving quality while adhering to time and cost budgets. ProgRouter introduces a multi-view task progress scorer that combines coarse workflow outcome regimes with fine-grained signals on subtask completion, progress trends, and workflow state quality. Then, a dual-path task progress predictor and an adaptive meta-gating mechanism estimate the progress gain for each candidate routed LLM. ProgRouter makes online step-wise routing decisions that balance progress gain, task time budgets, and long-term operating cost efficiency. Experiments on HumanEval Plus, MBPP, MATH-500, and ASQA, spanning agentic code generation, mathematical reasoning, and retrieval-augmented long-form question answering, demonstrate that ProgRouter reduces the operating cost relative to key baselines while maintaining strong task-solving performance.

- **现有方法的不足**：现有的级联路由（cascade routing）方法（如RouteLLM、MasRouter等）本质上是**一次性、查询级决策**，无法适应多步骤工作流中任务状态不断演化的特点。在多步协作场景中，每一步“应该用哪个LLM”取决于当前任务进度、剩余难度和预算消耗情况，而非仅由初始任务复杂度决定。
- **三个关键挑战**（论文明确提出）：
  1. 多智能体工作流是**开放式、有状态的**，静态基准或离线偏好数据无法满足在线、上下文感知的路由需求；
  2. 中间工作流状态**嘈杂且部分解析**，准确评估任务进度与剩余难度十分困难；
  3. 未来步骤与子任务难度**先验未知**，贪婪策略（总选最强模型）容易提前耗尽预算，而保守策略则浪费强模型能力，需要原则化的在线算法来平衡进度与长期成本。

### 二、论文提出的方法论

#### 1. 核心思想

ProgRouter将LLM智能体编排形式化为一个**在线约束优化问题**：通过实时估计当前工作流的任务进度以及每个候选LLM的边际进度增益（progress gain），在每一步做出即时且不可撤销的路由决策，以最大化任务性能，同时满足任务级时间/成本预算与系统级长期平均成本约束。

#### 2. 问题形式化

- 定义多智能体工作流为 `w = {C, R, M}`，其中C为协调器LLM智能体，R为预定义的worker角色集合，M为可用LLM模型集合。
- 优化目标：

```
max π   (1/W) Σ P(w)                        — 最大化平均任务性能
s.t.     Σ E(m_t) ≤ E_w                      — 每个任务的运营成本预算
         Σ Γ(m_t) ≤ Γ_w                      — 每个任务的时间预算
         (1/W) ΣΣ E(m_t) ≤ Ē                — 长期平均成本约束
```

#### 3. 多视图任务进度评分器

给定当前工作流状态 `s_t`，计算归一化进度分数 `g(s_t) ∈ [0,1]`，从**四个互补视角**评估：

| 视角 | 功能描述 |
|------|---------|
| **整体结果视图（Overall outcome view）** | 将状态映射为四种粗略状态（invalid / recoverable / partial success / complete），提供基础分数 `b(c_t)` |
| **子任务完成视图（Subtask completion view）** | 从协调器账本与worker执行反馈中计算已满足的任务需求比例 `r_t` |
| **进度趋势视图（Progress trend view）** | 通过分析最近若干步的进度变化（改进/停滞/回退）计算 `d_t` |
| **状态质量视图（State quality view）** | 结合相邻状态摘要的语义相似度（MiniLM嵌入）与结构化差异信号，计算 `e_t` |

最终通过层次化聚合得到：

```
g(s_t) = b(c_t) + α_c·r_t + β_c·d_t + γ_c·e_t
```

该评分器充当**轻量级领域适配器**——在新领域只需调整可观察的里程碑定义与粗略状态区间，下游算法模块保持领域无关。

#### 4. 双路径任务进度预测器

- **结构化路径（Structured path）**：基于表格特征向量（多视图进度分数、子任务完成度、历史调度记录、候选LLM决策等），使用树回归器（如随机森林/XGBoost）预测进度增益 `ŷ_str`。
- **语义路径（Semantic path）**：将工作流状态摘要与候选路由决策编码为密集语言嵌入（MiniLM），再用树回归器预测 `ŷ_sem`。
- **自适应元门控机制（Meta-gating）**：通过XGBoost元学习器根据在线状态动态组合两个路径的预测：

```
ŷ_t = P_meta(ŷ_str_t, ŷ_sem_t)
```

其原理是：当显式进度信号可靠时侧重于结构化路径，当状态包含隐性瓶颈时侧重于语义路径。

#### 5. 在线决策算法

- **虚拟成本队列（Virtual queue）**：受Lyapunov漂移加惩罚框架启发，维护虚拟队列：

```
Q_{w+1} = max{0, Q_w + ΣE(m_t) − Ē}
```

捕捉长期成本约束的违规累积。

- **进度缺口感知路由（Progress-gap-aware routing）**：将候选LLM的任务解决能力估值为：

```
P̂(m_t, s_t) = V · (1 − g(s_t)) · ŷ_t(m_t)
```

`(1−g(s_t))` 确保当任务仍有较大进步空间时，更强的LLM才会被调用。

- **预算感知成本惩罚**：定义随时间/成本消耗指数增长的惩罚系数 `cΓ_t` 和 `cE_t`，避免预算被过早耗尽。

- **最终路由分数**：

```
score(m_t) = P̂(m_t) − Q_w·(E(m_t) − Ē) − cΓ_t·Γ(m_t) − cE_t·E(m_t)
```

每一步选择 `m*_t = argmax score(m_t)`，综合平衡进度增益、系统级成本压力与任务级预算消耗。

- **在线预测器学习**：使用ε-greedy探索策略——以概率ε随机选择LLM收集无偏训练样本，以概率1−ε根据当前预测器选择最优路由。实测进度增益 `y_t = g(s_{t+1}) − g(s_t)` 作为监督信号，周期性更新预测器，ε逐渐衰减以从探索转向利用。

### 六、主要结论与发现

1. **固定单模型策略均不理想**：小模型因能力不足触发多次重复调度导致累计能耗高，大模型因单次调用能耗高而超预算；没有单一固定模型能在满足Ē的同时保持高性能。
2. **ProgRouter在所有基准上均取得最佳质量-成本权衡**：
   - HumanEval Plus：93.0%通过率（满足预算的方法中最高），能耗4,796J（在预算边缘内），比MasRouter高2.1%、比CASCADIA高8.2%；
   - MBPP：79.4%通过率，能耗最低（3,376J），时间最短（10.3s），**在所有指标上全面占优**；
   - MATH-500：84.3%通过率，能耗最低（6,112J）且时间最短（19.0s），比CASCADIA低3.5个百分点但成本显著降低；
   - ASQA：92.1%引用精确率（所有方法中最高），比MasRouter和CASCADIA高2.3%，同时满足19,000J预算。
3. **自适应路由分布揭示专业化模式**：ProgRouter在代码与数学任务中将大多数调度集中在高效小模型上（如HumanEval Plus中84.3%调用Qwen2.5-Coder 0.5B，MATH-500中91.0%调用Granite 4.1 3B），当进度预测器预期强模型能带来显著增益时才选择性调用大模型。
4. **消融实验确认所有组件均有贡献**：去除预测器使通过率从93.0%降至89.0%；去除预算惩罚降至87.8%；而朴素的“进度/成本”贪心策略仅达17.7%——说明**准确预测进度本身不够，需要完整的预算感知路由目标**。

1. **问题定位精准**：指出现有级联路由“一次性查询级决策”的本质缺陷，将路由从静态选择提升为在线、状态依赖的序贯决策问题，具有实际意义。
2. **多视图进度评分设计巧妙**：将粗略状态区间（稳定锚点）与细粒度信号（子任务完成、趋势、语义质量）结合，既能捕捉明显进度又能感知微妙变化，且生成密集的分步监督信号而非稀疏的最终结果。
3. **双路径+元门控预测器兼顾鲁棒性与灵活性**：结构化路径擅长显式信号，语义路径捕捉隐含线索，元学习器根据工作流状态自适应调节两者权重，设计合理。
4. **在线学习范式**：不需要离线训练数据，通过ε-greedy探索逐步累积路由经验，预测器随执行不断改进，适合实际部署场景。
5. **理论支撑扎实**：将Lyapunov漂移加惩罚框架应用于LLM路由，为长期成本约束提供了原则化的求解思路，而非依赖经验性启发式。
6. **评分公式设计有洞见**：`(1−g(s_t))` 进度缺口加权项，直观体现了“强模型应在任务仍有大量改进空间时使用”的经济学直觉。

### 八、不足与局限

1. **基准覆盖范围有限**：论文自身承认仅覆盖代码生成、数学推理和检索增强长问答三类任务；开放式网页导航、工具增强问答（tool-augmented QA）等智能体场景尚未验证，泛化性存疑。
2. **需要领域适配**：多视图进度评分器中的可观察里程碑定义与粗略状态区间需根据任务特征手工设定，虽然文中称其为“轻量级领域适配”，但即便如此也是一种人工成本；完全端到端自动学习进度表示仍是开放方向。
3. **模型库规模有限**：每个基准仅包含7~9个模型（且多为同一两家模型族的变体），未验证跨更多异构模型（如不同供应商、不同架构）时的路由表现。
4. **统计严谨性不足**：未报告多次运行的标准差、置信区间或显著性检验；MBPP和MATH-500各仅200个样本，ASQA仅100个样本，随机采样的代表性未加论证。
5. **能耗度量边界有限**：能量测量仅覆盖GPU（NVML功率积分），明确排除了CPU侧编排、主机内存、存储与网络通信能耗，虽然在系统层面这些占比通常较小，但在大规模部署时可能不可忽略。
6. **任务级预算约束的处理简化为指数惩罚函数**，其系数未给出调参分析；虚拟队列对单任务流的实际影响在消融中也较弱（92.7% vs 93.0%），其长期收益在有限评估流中未得到充分体现。
7. **伦理层面**：虽然论文提及路由模式监测和输出验证等建议，但未讨论路由决策可能引入的公平性问题（如某些用户群体被系统性地路由到较弱模型）以及数据隐私在协调器账本中的具体保护机制。
