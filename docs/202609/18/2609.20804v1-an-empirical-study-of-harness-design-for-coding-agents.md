## 摘要
编码执行框架决定了自主编码智能体如何将模型能力转化为长时程软件工程性能，但现有工作通常将框架作为整体系统进行评估，导致各个组件的有效性尚不明确。为了实现组件级比较，我们使用一个轻量级编码执行框架来研究该问题；该框架的执行循环固定不变，同时改变三个组件：规划、动作空间和上下文管理。在 SWE-Bench Verified 和 Terminal-Bench 2.1 上评估的四个模型中，我们评估了 176 个匹配设置，涵盖五种上下文管理策略、四种上下文窗口预算，以及针对规划和动作空间的目标消融。我们发现：(1) 随着上下文窗口预算收紧，上下文管理的价值日益增加，其大部分收益来自防止上下文溢出失败。(2) 在基于 LLM 的摘要之前先进行基于规则的省略，在上下文管理策略中提供最高的整体效率；而让被省略内容可恢复则增加了模型很少使用的机制，且未带来准确率提升。(3) 规划从较弱模型的准确率支架转变为较强模型的成本节省手段，而准确率几乎没有变化。(4) 预定义工具能提升 bash 能力较弱模型的表现，而具备 bash 能力的模型可以仅通过 bash 接口有效运行，并显著降低成本，尤其是在以命令行为中心的任务上。轨迹级分析解释了这些效应：上下文管理延长了执行轨迹，但没有显著改变智能体行为；规划改变了轨迹停止的位置；动作空间改变了代码编写的粒度。这些发现为模型感知和预算感知的框架设计提供了依据，并为评估未来的框架组件提供了一个模块化框架。

## Abstract
Coding harnesses shape how autonomous coding agents translate model capabilities into long-horizon software-engineering performance, yet existing work typically evaluates harnesses as monolithic systems, leaving the effectiveness of individual components unclear. To enable component-level comparisons, we study this question with a lightweight coding harness whose execution loop is fixed while three components are varied: planning, action space, and context management. Across four models evaluated on SWE-Bench Verified and Terminal-Bench 2.1, we evaluate 176 matched settings spanning five context-management strategies, four context-window budgets, and targeted ablations of planning and action space. We find that: (1) Context management becomes increasingly valuable as the context-window budget tightens, with most of its benefit coming from preventing context-overflow failures. (2) Staging rule-based elision before LLM-based summarization provides the strongest overall efficiency among the context-management strategies, whereas making elided content recoverable adds machinery that models rarely use and yields no accuracy gain. (3) Planning shifts from an accuracy scaffold for weaker models to a cost saver for stronger models, with little change in accuracy. (4) Predefined tools improve performance for models with weaker bash proficiency, whereas bash-capable models can operate effectively with a bash-only interface and achieve substantially lower cost, especially on command-line-centric tasks. Trajectory-level analysis explains these effects: context management extends execution trajectories without substantially altering agent behavior, planning changes where trajectories stop, and the action space changes the granularity at which code is written. These findings inform model- and budget-aware harness design and provide a modular framework for evaluating future harness components.

## 1. 核心问题与研究动机

- **背景**：LLM 正被用于自主完成真实软件工程任务（如关闭 GitHub issue、完成终端任务），其表现依赖于「编码执行框架（coding harness）」——即包裹模型、决定其行为方式的软件层。
- **核心矛盾**：框架内的关键组件（规划 scaffold、动作接口、上下文管理策略）并非无关紧要的实现细节，固定模型而改变框架可显著改变性能（如 Claude-Opus-4.5 在 OpenHands 上最好，Claude-Sonnet-4.5 在 SWE-Agent 上最好）。
- **现有研究不足**：已有工作多把 harness 当作**整体系统（monolithic）**评估，跨框架比较会混淆多种机制，无法判断性能差异究竟来自规划、工具设计、上下文管理还是它们与模型的交互。
- **核心研究问题**：harness 各组件是普遍有用，还是其有效性依赖于模型能力、任务类型与资源预算？
- **整体含义**：论文试图把 harness 设计从「整体调参」转变为**条件化（conditional）的系统问题**，为模型感知、预算感知的框架设计提供可迁移的诊断依据。

## 2. 方法论

### 2.1 核心思想
- 从零构建一个**轻量级、模块化**的 harness，**固定执行循环（ReAct loop）与其余支撑组件**，仅独立变化三个组件：规划（planning）、动作空间（action space）、上下文管理（context management），从而估计各组件的**条件效应（conditional effect）**。

### 2.2 关键技术细节

- **执行循环**：基于 ReAct，每轮包含推理 → 动作 → 观察三步。
- **规划组件**：
  - 通过系统指令 + 首轮提醒 + `update_plan` 工具维护持久化任务计划；计划在每轮作为独立注入块附加，不写入对话历史。
  - 关闭时移除全部规划指令、提醒、计划注入与工具，其余保持不变。
- **动作空间组件**：
  - **预定义工具集**：`read_file`、`write_file`、`edit_file`、`list_files`、`glob_files`、`grep_text`、`web_fetch`、`bash`，每个工具有类型化参数 schema 与协议/错误/副作用说明。
  - **bash-only**：移除预定义文件/搜索/网页工具，仅保留 `bash`。
  - 该干预是「捆绑式接口变更」，同时改变工具可用性、接口提示、文件状态跟踪与编辑后诊断，而非仅隔离工具数量或动作粒度。
  - 排除 web search，以防泄露 SWE-Bench 的 ground-truth patch。
- **上下文管理组件**：三种可组合机制
  - **M1 省略（elision）**：把陈旧工具观察的正文替换为短桩（stub）。
  - **M2 召回（recall）**：将被省略内容存外部文件系统，暴露 `recall_event` 工具按需取回，使省略可逆。
  - **M3 摘要（summarization）**：由同一被评估模型在独立无工具调用中，把最旧的中段事件折叠为滚动摘要。
  - **阈值机制**：软阈值 B1（省略触发）< 硬阈值 B2（摘要触发）；前言（system prompt + 初始任务）与至少两轮的近期窗口保持原文，仅压缩中间区域。
- **五种策略分级（Tier）**：
  | Tier | M1 | M2 | M3 |
  |---|---|---|---|
  | T0 | ✗ | ✗ | ✗（溢出即报错终止）|
  | T1 | ✓ | ✗ | ✗ |
  | T2 | ✓ | ✓ | ✗ |
  | T3 | ✗ | ✗ | ✓ |
  | T4 | ✓ | ✓ | ✓（先省略后摘要，默认配置）|
- **固定支撑组件**（所有消融中不变）：
  - **安全**：workspace guard（防路径逃逸/符号链接）、read-before-write 校验（含内容哈希检测外部修改）、allow/ask/deny 权限层；工具错误作为观察返回而非抛异常。
  - **编辑后诊断**：对 Python 文件用 ruff/pyflakes/语法回退做快速只读检查，结果追加到工具返回。
  - **卡死检测**：监控工具日志中的连续相同调用，达到阈值注入提醒，连续失败 8 次则提前终止。

## 3. 实验设计

### 3.1 模型
- **Nemotron-3** 三个规模：30B、120B、550B（同族能力轴）。
- **Mistral-Medium-3.5-128B**（跨族对照）。
- 定价按 OpenRouter：$0.05/$0.20（30B）、$0.08/$0.45（120B）、$0.50/$2.20（550B）、$1.50/$7.50（Mistral）。

### 3.2 基准与指标
- **SWE-Bench Verified**：500 个经人工验证的真实 GitHub issue（仓库级问题解决）。
- **Terminal-Bench 2.1**：89 个命令行环境端到端任务。
- 指标：**任务成功率（SR）** 与 **平均每任务成本（$）**。

### 3.3 对比设置
- **上下文管理消融**：T0–T4 × 4 种窗口预算（32k/64k/96k/128k）= 每模型-基准 20 个设置。
- **组件消融**（在 T4/128k、全工具集、开启规划下）：
  - `−plan`：关闭规划。
  - `bash only`：替换为纯 shell 接口。
- 每模型-基准 22 个设置 × 4 模型 × 2 基准 = **176 个实验设置**。
- **统计方法**：对任务配对结果用双侧精确 McNemar 检验，Benjamini–Hochberg 控制 FDR 在 0.05。

### 3.4 实现细节
- 服务：SGLang，BF16，Temperature=0，top-p=0.95，单轮输出上限 16,384 tokens。

- 阈值：软/硬阈值取可用窗口的 0.6/0.85，近期窗口预算 0.3（至少两轮）。
- 工具结果截断至 24k 字符，每步最多 8 个只读工具并行。

### 3.5 轨迹分析
- 用 LLM 判官（GPT-5.5，reasoning effort high，T=0.6）对轨迹打标：
  - SWE-Bench 轮级五阶段：Localize / Reproduce / Fix / Verify / Other。
  - SWE-Bench 失败阶段归因：file loc. / line loc. / patch / verification（取最早失败阶段）。
  - Terminal-Bench 动作级 10 符号（I/S/C/M/E/X/T/V/N/G），归为 Understand / Write code / Verify / Other。

## 6. 主要结论与发现

1. **上下文管理价值随预算收紧而增大**：管理组 vs T0 的成功率差在 32k/64k/96k/128k 上从 35.7 → 15.9 → 5.5 → 2.7 个百分点（SWE-Bench），Terminal-Bench 为 9.5 → 7.5 → 4.8 → 2.8；T0 溢出失败率从 78.7% 降至 8.7%，而所有管理 tier 溢出失败为 0。收益主要来自**防止过早截断**。
2. **T4（先规则省略后 LLM 摘要）效率最佳**：在 8 个模型-基准面板中 7 个成本最低；峰值上下文比最低；早期省略减少了对昂贵摘要调用的依赖。
3. **召回机制（M2）几乎无用**：64 个 T2/T4 设置中 56.3% 从未调用 `recall_event`，调用率中位数为 0；T2 vs T1 平均差异 −0.36 个百分点，无准确率增益。
4. **规划的角色随能力迁移**：
   - 弱模型（30B）：SWE-Bench +11.6 点、Terminal-Bench +4.5 点，成本上升（防止过早终止，中位轨迹从 5 轮→40 轮）。
   - 强模型（550B、Mistral）：主要**降本**（SWE-Bench 约 −30%/−32%），准确率小幅下降（−2.0/−0.4 点），主要减少**编辑后冗余验证**。
   - 中间能力（120B）依赖任务类型。
5. **动作空间交叉效应**：
   - 预定义工具利好 bash 弱模型（30B：+15.0% SWE-Bench、+10.1% Terminal-Bench）。
   - bash 强者（550B）用 bash-only 反而 +3.6%/+5.6% 准确率且成本 −53%/−30%，调用更少（更复合的命令）。
   - Mistral 呈现**任务类型依赖的反转**：SWE-Bench 全工具更好（+23.2%），Terminal-Bench bash-only 更好（+6.7%），因为后者更 shell 中心（全工具下 71.9% 动作走 bash）。
6. **轨迹机制解释**：
   - 上下文管理**延长轨迹但不显著改变行为**（128k 下各 tier 轨迹形状几乎不变）。
   - 规划**改变轨迹停止位置**（弱模型从过早放弃到完成首次编辑；强模型削减验证尾部）。
   - 动作空间**改变代码书写粒度**：bash-only 减少重复补丁（如 550B 4.6→1.5），Terminal-Bench 上 create/replace 占比从 28%→64%（30B）等，即用更少、更粗的交互完成同等工作。

## 7. 优点

- **模块化受控实验**：固定执行循环与支撑组件，独立变化三个组件，显著优于整体式 harness 比较。
- **双维度扫描**：同时沿「上下文窗口预算」和「模型能力（同族规模 + 跨族）」两个轴刻画条件效应，发现组件价值并非普适。
- **组件级细粒度**：把上下文管理拆为 M1/M2/M3 并组合成 5 个 tier，能定位收益来源（如证明 M2 无效）。
- **多目标评估**：同时报告成功率与成本，揭示准确率-成本权衡而非单一指标。
- **轨迹级证据**：用经人工验证（κ≈0.93）的 LLM 判官标注，把聚合结论追溯到行为机制（轨迹长度、阶段构成、编辑粒度、失败阶段）。
- **可迁移的诊断价值**：结论不绑定特定模型，为未来模型提供 harness 设计的「条件化决策表」。
- **工程细节透明**：附录完整给出提示词、工具描述、stuck-detection 文本、判官提示词，可复现性强。

## 8. 不足与局限

- **实现特定性**：结论针对本文的具体实现（单一规划提示与 `update_plan` 机制、单一阈值式上下文策略、捆绑式动作接口），并非普适最优 harness。
- **动作空间不可分解**：同时变化工具可用性、接口提示、文件状态跟踪与编辑后诊断，无法隔离工具数量或动作粒度的影响。
- **设计空间覆盖有限**：规划与动作空间仅在 T4/128k 单点消融，缺乏全因子实验；无法确认效应在其他组合下是否持续。
- **统计功效有限**：每设置每任务仅一次运行，无重复；Terminal-Bench 仅 89 题，多数对比不显著，结论依赖跨模型一致性方向。
- **外部效度受限**：仅 4 个模型、2 个基准，SWE-Bench Verified 仅 Python；模型规模只是能力的**不完美代理**（训练差异、工具接口先验暴露、原生 shell 熟练度均可能影响结果，Mistral 的基准依赖接口偏好即为证据）。
- **偏差风险**：使用 LLM 判官做轨迹标注（虽有高一致性但仍有系统性偏差可能）；模型定价采用第三方（OpenRouter）数据。
- **应用限制**：论文明确警告，报告的「交叉点（crossover points）」在迁移到其他模型族、harness 实现或非软件工程任务前需重新验证。
