## 摘要
代码智能体在仓库中定位正确代码上花费了大量精力。当前实践中主要有两种方法。在语义搜索中，智能体从预先构建的仓库向量索引中检索代码块。在深度智能体搜索（也称为子智能体grep搜索）中，规划智能体将探索任务委托给一个独立的子智能体，该子智能体在隔离的上下文窗口中工作，只返回精炼后的结果。第二种设计被认为是良好的上下文工程实践，其目的是保护主智能体免受上下文污染（也称为上下文腐化），即随着不相关材料在上下文窗口中累积而导致准确性下降的问题。近期的代码智能体（如Claude Code、Codex、Antigravity等）已迅速采用该方法，但关于它是否能产生更好的答案，证据尚少。我们在SWE-QA（一个仓库级代码问答基准）上比较了这两种方法。语义搜索正确回答了65.2%的问题，而深度智能体搜索仅有46.2%，且语义搜索生成每个正确答案的成本不到后者的一半。为解释这一差距，我们将每次失败的运行编码为一份失败模式分类表。该分类表表明，深度智能体搜索并未消除失败，反而引入了一类新的失败：其失败中最大的一部分（41.8%）发生在规划器与其子智能体之间的交接环节，且这些失败通常是静默的，最终以流畅而自信的错误答案结束。深度智能体搜索解决了一个真实存在的问题，并且目前已成为许多代码智能体的首选设计。然而，我们的结果表明，它所提供的保护可能并非没有代价，并且对于可以索引的仓库上的只读问题，检索是更强且更便宜的选择。

## Abstract
Code agents spend much of their effort simply locating the right code inside a repository. Two approaches dominate current practice. In Semantic Search, the agent retrieves code blocks from a vector index built from the repository in advance. In Deep Agentic Search (also known as grep-search by subagent), a planning agent delegates the exploration to a separate subagent that works in an isolated context window and returns only a condensed result. The second design, which is considered good context engineering practice, exists to protect the main agent from context pollution (also known as context rot), the loss of accuracy that occurs as unrelated material accumulates in the context window. Recent code agents (such as Claude Code, Codex, Antigravity, etc) have adopted it quickly, but there is little evidence on whether it produces better answers. We compare the two approaches on SWE-QA, a benchmark for repository-level code question answering. Semantic search answered 65.2% of questions correctly against 46.2% for deep agentic search, and it produced each correct answer at less than half the cost. To explain the gap, we then coded every failed run into a taxonomy of failure modes. The taxonomy shows that deep agentic search did not remove failures but introduced a new class of them: the single largest share of its failures, 41.8%, occurred at the hand-off between the planner and its sub-agent, and these were usually silent, ending in a fluent and confident answer that was wrong. Deep agentic search addresses a real problem and is now the preferred design in many code agents. However, our results show that the protection it offers may not be free, and that for read-only questions over a repository that can be indexed, retrieval was the stronger and cheaper option.

## 1. 核心问题与整体含义（研究动机与背景）

- **研究定位**：针对仓库级（repository-level）代码问答任务，系统比较当前两种占据主导地位的代码智能体搜索范式——**语义搜索（Semantic Search）** 与**深度智能体搜索（Deep Agentic Search）**。
- **核心矛盾**：深度智能体搜索通过将探索任务委托给在隔离上下文窗口中工作的子智能体，仅向主智能体返回精炼结果，以此避免"上下文污染/腐蚀"（context pollution/rot）。该设计被Claude Code、Codex、Antigravity等主流代码智能体迅速采用，被认为是良好的上下文工程实践，但缺乏实证证据证明其优于传统方法。
- **研究意义**：这是**首个**系统性地将"基于索引的检索智能体"与"委托子智能体进行隔离探索的Deep Agent"进行头对头比较的实证研究，其结论直接挑战了当前业界对深度智能体搜索的偏好，为实践者的技术选型提供了数据驱动的依据。

## 2. 方法论：核心思想与技术细节

- **总体思路**：本研究**不提出新方法**，而是以中立态度对两种范式进行受控对比实验，并辅以成本分析和失败模式分类来解释实验结果。
- **范式一：语义搜索（Semantic Search）**
  - 架构：基于LangChain的**ReAct agent**，严格限制为SWE-QA基准协议规定的三个工具：仓库结构查询（`get_repo_structure`）、向量索引检索（`search_rag`）、文件读取（`read_file`），无shell访问、无文件写入、无规划工具。
  - 检索配置：RecursiveCharacterTextSplitter切分，chunk size 500 token、overlap 50 token；使用`text-embedding-3-small`（1,536维）生成稠密向量；Chroma向量数据库按仓库独立建库；余弦相似度检索，每次`search_rag`取top-k=10。
  - 工作方式：预先对仓库建立向量索引，在推理时通过多轮检索查询逐步精化上下文。
- **范式二：深度智能体搜索（Deep Agentic Search）**
  - 架构：基于LangChain官方`langchain-deep-agents`库的**Deep Agent**，使用默认工具集：任务列表规划（`write_todos`）、子智能体委托（`task`）、文本搜索（`grep`）、文件列表与通配（`ls`、`glob`）、文件读取（`read_file`）。
  - 工作方式：规划器（orchestrator）通过任务列表维护高层计划，将嘈杂的探索循环委托给拥有独立上下文窗口的子智能体；子智能体吸收原始输出并过滤，仅向规划器返回精炼结果，从而保持规划器上下文干净。
- **关键设计选择**：
  - 两种范式的工具集差异是其**构成性特征**而非混杂变量——若给ReAct agent加上规划与子智能体委托能力，它就变成了Deep Agent。
  - 固定所有非范式构成性因素：相同的15个仓库、720个问题、4个模型、相同的评判者和评分标准；每个模型与自己跨架构对比（配对设计）；两个agent均基于LangChain框架实现。
  - 评判采用Claude Sonnet 4.6（与所有回答模型不同供应商、不同模型家族），按5个维度（正确性、完整性、相关性、清晰度、推理）打分，总分0-100，Pass≥70、Partial 50-70、Fail<50。
  - 失败分析采用双轴编码：**机制轴**（协调失败、检索/定位失误、证据不足、证据误读、非终止循环、证据收集失败）记录根本行为原因；**症状轴**（无答案、前提否定、错误实体/机制、事实错误、不完整/浅薄）记录答案的问题形态。

## 3. 实验设计

- **数据集/基准**：**SWE-QA**基准（Peng et al., 2026a），覆盖15个广泛使用的开源Python仓库（12个来自SWE-bench，3个来自SWE-bench-Live），仓库规模从约1.3万行Python到超过86万行不等；每仓库48个问题，共**720个问题/条件**；问题分为What、Why、Where、How四类，比例大致相等。使用基准原版数据集和评分标准，未做修改。
- **对比模型**：在4个语言模型上交叉运行两种架构，形成8个实验条件（4模型×2架构）：
  - Gemini 2.5 Flash、Gemini 2.5 Pro、Gemini 3 Flash（同一供应商、不同能力层级与代码代际）
  - Qwen3-235B（开源权重模型，跨供应商验证）
- **对比方法/基线**：仅对比语义搜索（ReAct agent + 向量索引）与深度智能体搜索（Deep Agent + 子智能体委托）两种范式，无第三方加入。
- **统计检验**：Pass率差异用精确McNemar检验，分数差异用Wilcoxon符号秩检验，效应量用Cliff's delta（95% bootstrap置信区间）和配对标准化均差dz；跨4个模型使用Benjamini-Hochberg FDR校正。
- **评判者有效性验证**：3名外部软件工程师（≥2年经验，非论文作者）对800条答案（每条件100条）进行盲评，与LLM judge的一致性达到substantial至almost perfect水平（判定Cohen's kappa=0.74，数值Pearson r=0.83）。

## 6. 主要结论与发现

- **RQ1（准确率）**：
  - 语义搜索Pass率为**65.2%**，深度智能体搜索为**46.2%**；Fail率分别为21.9% vs 34.4%。
  - 方向在4个模型上完全一致，但幅度差异大：Gemini 2.5 Flash差距5.6个百分点（小）、Gemini 2.5 Pro差距10.0（中等）、Qwen3-235B差距10.6（中等）、Gemini 3 Flash差距**49.6个百分点**（巨大）。所有配对检验在FDR校正后均显著。
  - 阈值敏感性分析（Pass阈值从50扫到90）：语义搜索在所有模型、所有阈值下均高于深度智能体搜索，最小差距3.8个百分点，结论不依赖阈值选择。
  - Deep仅在15个仓库中的1个（django）上领先3.0分；语义搜索领先幅度随仓库规模增大而收窄（Spearman rho=-0.69, p=0.004），但最大仓库sympy（86.1万行）仍偏向语义搜索13.7分——是收窄而非反转。
- **RQ2（成本与效率）**：
  - Deep在4个模型上的每问题输入token消耗均更高（Qwen3-235B上差距最大：34k vs 761k）；单价成本每模型均更高。
  - **每次正确回答的成本**：混合4个模型，语义搜索约0.32美元 vs Deep约0.74美元（**Deep贵约2.3倍**）。
  - 精度-成本平面上Semantic点均位于左上（更高精度更低成本）区域，Deep点均位于右下。
  - 每问题投入token/工具调用数与得分呈平坦至负相关——更多努力并未换来更高准确率。
  - 延迟无一致排序（受执行环境影响，仅作参考）。Deep开销比与仓库规模无显著关联（15个仓库检验力不足，结论不明确）。
- **RQ3（行为与失败模式）**：
  - Deep约68.8%的工具调用发生在委托的子智能体内部（2,878次运行中2,395次至少委托一次，平均每运行2.1次委托，每次委托内部约10次调用）。
  - 失败机制分布差异显著（χ²=508.8, Cramer's V=0.56）：Deep最大失败类别是**协调失败（coordination breakdown）**，占其所有失败的**41.8%**（Semantic为0）；Semantic失败集中于检索/定位失误（53.6%）。排除定义性机制后差异仍显著（χ²=147.2, Cramer's V=0.35）。
  - **静默性关键发现**：91%的协调失败仍产出流畅、自信的错误答案而非报告错误——失败对用户不可见。
  - 症状分布的架构间差异远小于机制差异（χ²=43.8, Cramer's V=0.16），即两种架构产生形态相似的错误答案但通过不同机制达成。
  - Deep比Semantic更可能完全无答案（24.2% vs 12.7%）。
- **最终结论**：深度智能体搜索的上下文保护**并非免费**——在可索引仓库的只读问答场景下，语义检索是更准确、更经济的选择。该结论的适用边界被严格限定于"单轮、只读、可索引仓库"场景，不适用于多任务长会话或多轮代码编辑等场景。

## 7. 优点与亮点

- **首创性**：首次系统对比"索引检索agent"与"委托子智能体的Deep Agent"两种范式，填补了文献空白。
- **中立且可复现**：不提出新方法，使用广泛采用的开源框架默认配置（LangChain ReAct + langchain-deep-agents），无供应商特定调优。
- **实验设计严谨**：
  - 配对设计（同模型内对比）隔离范式效应；多家供应商模型交叉验证排除单一供应商偏差。
  - 同时报告价格无关指标（token数）与价格相关指标（美元），提升时效性。
  - 对自动judge进行人类验证（kappa=0.74, Pearson r=0.83），增加了结果可信度。
  - 阈值敏感性分析和整仓库bootstrap重采样增强了结论稳健性。
- **分析全面**：准确率、成本（含每正确答案成本）、行为（工具使用、轨迹长度）、失败机制+症状双轴分类四维一体，为理解差距提供了机制层面的解释。
- **实践洞察深刻**：指出Deep失败的静默性（91%协调失败仍输出流畅错误答案）——这是使用体验层面极具价值的安全警示；讨论了深度智能体搜索在"上下文卫生"（长会话场景）和"不可索引环境"中的价值边界，避免了对该范式的全盘否定。

## 8. 不足与局限

- **实验覆盖有限**：
  - 单一基准（SWE-QA）、单一语言（Python）——无法确认结论是否推广至Java/TypeScript等多语言仓库。
  - 仅4个模型、15个仓库，未覆盖更多模型和更大规模仓库；仓库规模趋势仅在15个数据点上统计检验，缺乏更大仓库的验证。
- **架构实现绑定**：每种范式仅通过一个特定harness实现（LangChain家族），其他生产框架（OpenHands等）可能产生不同结果；未做跨harness敏感性分析。
- **场景狭窄**：只评估单轮只读问答，无法捕捉Deep在长会话、多任务场景中"保持规划器上下文干净"的核心设计价值——论文明确承认该收益在单轮问答中无法体现为准确率优势，因此结论不能外推至实际的长期agent工作流。
- **潜在偏差风险**：
  - 检索配置（chunk大小、top-k）和Deep工具集均为单点配置，未做消融；不同配置可能改变差距幅度。
  - 仓库可能在模型训练数据中（论文做了泄漏检查，但仅描述性——SWE-bench-Live子集上语义搜索优势反而更大，与记忆驱动假说方向相反）。
  - 延迟指标受环境噪声影响，论文不基于它下结论。
- **成本度量范围**：未计入开发/维护索引流水线及Deep agent配置调优的人力成本；每正确答案成本基于当时价格，价格变动会影响绝对值但不影响相对排序。
- **统计局限**：15个仓库间的嵌套效应虽用bootstrap处理，但仓库数少限制了对仓库级异质性的推断能力。
