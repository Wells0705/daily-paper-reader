## 摘要
大语言模型智能体越来越依赖长期记忆来支持多会话交互和个性化。然而，现有的智能体记忆系统围绕“仅向前演化”设计，不断累积、整合和覆写知识，缺乏检查、版本化或回退先前状态的原则性机制。这使得智能体在修正、概念漂移和记忆损坏时表现脆弱，尤其是在它们已经接触了后续信息之后。我们提出ChronoMem，这是一个面向智能体记忆的语义版本控制层，集成在Google的生产就绪开源智能体开发套件中。ChronoMem在每次记忆写入时提交整体记忆快照，维护结构化版本历史，并通过混合词汇与语义检索、排名融合和重排序，将撤销意图映射到具体历史版本，从而支持自然语言回滚请求。我们还引入了一种暴露后评估协议，通过让智能体回答查询和总结历史来测试其在回滚后是否能以反事实方式表现，仿佛未来的更新从未发生过。在扩展了动态记忆状态和回滚任务的长时对话基准上，相对于仅提示和仅检索基线，ChronoMem显著提升了回滚一致性的问答和历史总结性能，同时在语义版本选择上实现了强劲性能。据我们所知，ChronoMem是首个针对大语言模型智能体中系统性语义全局记忆回滚的开源系统和基准。

## Abstract
LLM agents increasingly rely on long-term memory to support multi-session interaction and personalization. However, existing agent memory systems are designed around forward-only evolution, continuously accumulating, consolidating, and overwriting knowledge, with no principled mechanism to inspect, version, or revert prior states. This makes agents brittle under corrections, concept drift, and memory corruption, particularly after they have already been exposed to subsequent information. We present ChronoMem, a semantic version-control layer for agentic memory integrated into the production-ready, open-source Agent Development Kit by Google. ChronoMem commits whole-memory snapshots at each memory write, maintains structured version histories, and supports natural-language rollback requests by mapping undo intents to concrete historical versions through hybrid lexical and semantic retrieval, rank fusion, and reranking. We further introduce a post-exposure evaluation protocol that tests whether an agent can behave counterfactually after rollback by answering queries and summarizing history as if future updates had never occurred. On long-horizon conversational benchmarks augmented with evolving memory states and rollback tasks, ChronoMem substantially improves rollback-consistent question answering and history summarization relative to prompt-only and retrieval-only baselines, while achieving strong performance in semantic version selection. To our knowledge, ChronoMem is the first open-source system and benchmark for systematic semantic global memory rollback in LLM agents.

## 2. 方法论

### 2.1 核心思想
- 将智能体长期记忆建模为**版本化状态机**：每一次记忆写入产生一个新的全局快照（commit），回滚即恢复某个历史快照，并将 `HEAD` 指针移至该版本，使后续所有读取**只对恢复后的版本可见**（接口不变量）。
- 采用**事件溯源（Event Sourcing）**思想：维护 append-only 事件日志 `L = <e1, e2, …, ej>`，版本 `vj` 的快照 `S(vj)` 由日志前缀物化而来，避免回滚时重放全部日志，以存储换速度。

### 2.2 四阶段流水线
- **Stage 1 — 版本构建（commit-on-write）**：每次记忆写入后（如用户说"I moved to NYC"），在一个事务中：追加事件→生成新版本 ID→构建提交描述符→物化全量快照→持久化→更新 `HEAD`。见 Algorithm 1。
- **Stage 2 — 版本索引（语义提交描述符）**：每个版本 vj 用一个描述符 dj = {delta, summary, op, labels} 索引，其中 delta 是操作级变化明细、summary 是自然语言摘要、op 是更新类型、labels 是时间元数据。检索在描述符层进行，**开销取决于版本数而非快照大小**。
- **Stage 3 — 自然语言→版本映射**：给定回滚请求 q，并行执行：
  - **词法检索**：SQLite FTS5 + BM25 排名；
  - **稠密检索**：对描述符做向量相似度检索；
  - **RRF 融合**：`RRF(vj|q) = Σ_{m∈{lex,sem}} 1/(k0 + rank_m(vj))`，k0 常取 60；
  - **重排序**：用更强的相关性模型（如 Cohere Rerank-3.5 交叉编码器）对 top-K 候选重排，选出最终版本 v̂。
- **Stage 4 — 确定性回滚执行**：`RollbackToVersion(app, user, vid)` 从快照恢复状态→设置 `HEAD`→截断后续版本（保持线性历史）→尽量同步检索后端索引（幂等操作）。该阶段是确定性的，与版本选择解耦，便于解释错误来源。

### 2.3 关键设计区分
- 显式区分两类 API：
  - `rollback_to_version(version_id)`：ID 驱动的确定性原语；
  - `rollback_to_version_by_nl_query(query)`：自然语言驱动的语义回滚，组合了检索+原语。
- 明确**不**试图撤销智能体记忆之外的任意外部副作用（如第三方服务状态），与现有 rewind 机制的边界一致。

## 3. 实验设计

### 3.1 数据集与协议
- **两个基准**：
  - **LoCoMo**：超长多会话对话基准，用于评测回滚一致的问答（QA）与事件/历史摘要；
  - **MemoryAgentBench（MAB）**：增量多轮交互记忆基准，用于模拟频繁更新下的语义回滚（QA 只取 Accurate Retrieval 子集，摘要取 En.Sum 子集）。
- **事后暴露回滚协议（Post-exposure rollback protocol）**：
  1. **暴露阶段**：智能体完整吸收交互流到最终状态 vT；
  2. **回滚阶段**：发出自然语言回滚请求，恢复到目标版本 v̂；
  3. **执行阶段**：在恢复后的状态下执行下游任务（QA 或摘要），检验反事实行为——智能体已见过 v* 之后的信息，但必须表现得好像这些信息从未发生过。
- **回滚查询构造**：基于数据集标注锚点（如 LoCoMo 的证据跨度、MAB 的更新边界），用 (i) 基于真实标注的模板 + (ii) LLM 生成的多样化改写；明确**禁止在查询中使用版本 ID、时间戳或会话索引**，避免平凡化版本选择。

### 3.2 评测指标
- **RQ1（语义版本选择）**：Recall@1、Recall@5（候选集内排名准确性）、Scope@2（最终选中版本与真实版本的时间距离 ≤2 的概率，用于诊断"近失"行为）。
- **RQ2（回滚一致 QA）**：LoCoMo 用 F1，MAB 用任务准确率；同时检测答案是否泄漏 v* 之后的事实。
- **RQ3（回滚一致摘要）**：ROUGE-1（LoCoMo）、F1（MAB）。

### 3.3 对比基线
- **Prompt-only rollback**：只给自然语言回滚指令，不改底层记忆状态——检验纯指令跟随能力；
- **Full-history prompt rollback**：把完整历史（含 v* 之后内容）全部放入上下文，指示模型"仿佛"回滚——最大污染的强基线；
- **Retrieval-only rollback（RAG-only）**：用稠密检索 top-k 相关记忆片段，不恢复版本化快照——隔离显式版本恢复的增益。

## 6. 主要结论与发现

- **RQ1（版本选择）**：ChronoMem 在两个数据集上均大幅超越基线的 Recall@1/Recall@5。LoCoMo 上 Recall@1 从 Hybrid 的 12.0% 提升至 20.5%；MAB 上从 24.3% 提升至 33.4%。Scope@2 的提升更为显著（LoCoMo：17.9%→31.2%；MAB：40.5%→58.0%），说明**重排序对区分语义相似相邻版本至关重要**。
- **RQ2（回滚一致 QA）**：ChronoMem 在所有骨干模型上均优于最强非版本化基线（RAG-only）。LoCoMo 上 F1 最高达 38.5%（Qwen2.5-7B，mian RAG-only 为 27.1%）；MAB 上优势更明显（最高 55.1% vs. 34.2%）。Prompt-only 接近随机水平（≤3%），说明**事后暴露的信息污染难以靠提示工程克服**。
- **RQ3（回滚一致摘要）**：ChronoMem 在两个数据集的摘要任务上都最优。LoCoMo ROUGE-1 最高 0.25（Llama-3.1-8B），较 RAG-only 提升约 0.04；MAB En.Sum F1 最高 14.0%，远高于 RAG-only 的 3.0%。
- **总体判断**：回滚一致性是**架构属性**而非推理能力的涌现结果；全局快照恢复 + 版本级索引 + 混合检索是支撑语义全局回滚的有效组合。

## 7. 优点

- **问题定位精准**：识别出"仅前向记忆"这一被忽略的盲区，首次将版本控制、事件溯源、混合检索等成熟系统技术系统化应用于智能体记忆。
- **架构设计优雅**：将回滚分解为"NL→版本"的检索问题与"确定性恢复"的数据平面原语，解耦选择错误与恢复正确性，使错误可归因、评测可解释。

## 8. 不足与局限

- **并发与事务语义未评测**：实现采用每用户锁 + SQLite 单写者事务，但未实验评估高并发同时提交/回滚时的竞争、队列和写放大问题（论文自我承认）。
- **仅支持线性历史**：当前实现是 Git "reset" 风格——回滚后截断之后版本，不支持分支时间线（branch）、合并（merge）、保留废弃分支等更丰富的版本管理语义。
- **基准适配局限**：LoCoMo 和 MAB 并非为版本回滚设计，论文用受控锚点+LLM 改写生成的查询，分布可能与真实世界中模糊、不完整、多义的"撤销"意图有差距。
- **测试规模可控但有限**：骨干模型仅限 7-8B 参数区间（Llama-3.1-8B / Qwen2.5-7B / Mistral-7B），未验证在更大参数量（如 70B+）模型上的表现；也未覆盖 GPT-4o/Claude 等闭源主流模型。
- **检索后端同步是 best-effort 幂等操作**：在快照恢复成功后，若持久的向量/全文索引同步失败，可能出现本地状态与检索后端不一致，论文未对这种故障场景做敏感性分析。
- **存储开销**：commit-on-write 全量快照的存储成本随版本数线性增长，论文虽指出以存储换恢复速度，但未给出实际存储开销的数据。
- **无统计显著性检验**：各方法之间的差异未报告置信区间或显著性水平，部分差距（如 MAB 摘要中 Llama-3.1-8B 的 13% vs. 14% 内部差异）能否在更多随机种子下复现不够明确。
- **外部环境回滚明确不覆盖**：无法撤销第三方服务副作用、应用级资源等外部依赖，这一边界与现有机制一致，但对真实复杂代理场景的限制需要明确告知。
