## 摘要
大型语言模型（LLM）越来越多地作为自主智能体执行复杂、长时程的程序性技能。现有的智能体运行时通过不断将观察、动作和中间推理轨迹附加到不断增长的对话历史中来维持执行，这会导致延迟退化并在长时程中引发上下文污染故障。我们提出了SKILL.state，一种运行时架构，用显式的、可变的执行状态取代仅追加的对话历史。在每个执行步骤中，模型仅接收不变的技能规范、当前的结构化执行状态和最新的观察。中间推理在生成经过验证的状态更新后立即被丢弃，防止提示随执行历史增长。在多种数据集、模型和执行环境中，SKILL.state提高了任务准确率，同时大幅减少了累计令牌消耗。我们的结果表明，显式执行状态是一种有效的、与架构无关的抽象，适用于可扩展的长时程智能体技能。

## Abstract
Large Language Models (LLMs) increasingly act as autonomous agents executing complex, long-running procedural skills. Existing agent runtimes maintain execution by continually appending observations, actions, and intermediate reasoning traces to an ever-growing conversation history, causing latency degradation and context-poisoning failures over long horizons. We present SKILL.state, a runtime architecture that replaces append-only conversational history with an explicit, mutable execution state. At each execution step, the model receives only the immutable skill specification, the current structured execution state, and the latest observation. Intermediate reasoning is discarded immediately after producing a validated state update, preventing prompt growth with execution history. Across diverse datasets, models, and execution environments, SKILL.state improves task accuracy while substantially reducing cumulative token consumption. Our results demonstrate that explicit execution state is an effective and architecture-agnostic abstraction for scalable long-horizon agent skills.

## 1. 核心问题与整体含义（研究动机与背景）

- **问题根源**：当前主流 LLM 智能体运行时普遍采用“对话式执行模型”，即在每一步都将原始技能规范 + 不断增长的推理、动作、观察和工具输出历史拼接为提示词，输入给模型。
- **核心痛点**：
  - 提示词体积随执行步数线性增长（累积 token 消耗呈 O(T²) 二次增长），导致推理延迟增加、成本飙升；
  - 过时的观察与推理残留在上下文中，形成“上下文污染”（context poisoning），模型需要持续区分“当前事实”与“历史痕迹”；
  - 在长时程（long-horizon）程序性技能执行中，正确性越来越依赖从庞杂文本历史中重建状态，而不是直接利用当前世界状态。
- **研究意义**：作者提出，长时程智能体执行不仅是“推理问题”，更是“系统工程问题”。现有的摘要、检索、压缩类记忆方案仍然保留了同样的执行语义（用文本重建历史），没有从根本上解决状态维护的困境。

## 2. 方法论：核心思想、关键技术细节与算法

- **核心思想**：将程序性技能执行重新定义为**显式的状态转移过程**，而非对话历史的累积。执行状态成为运行时的一等抽象，中间推理仅作为临时计算被保留、验证后即丢弃。
- **每步输入**（公式）：
  ```
  At = (P, Σt, Ot)
  ```
  其中 P 为不可变的程序性技能规范，Σt 为第 t 步的结构化执行状态，Ot 为最新环境观察。模型**不会**看到之前的观察、动作或推理轨迹。
- **状态 Schema**：按领域一次设计，跨任务复用。例如 InterCode CTF 的 100 个任务共享同一个 5 字段 schema（discovered_flags、tested_hypotheses、active_files、working_dir、cmd_summary）。
- **单步生成**：模型在当前上下文 (P, Σt, Ot) 下生成三元组：
  ```
  (Rt, ΔΣt, at)
  ```
  Rt 为多步 Chain-of-Thought 推理轨迹；ΔΣt 为结构化状态更新（JSON 字典，支持键的修改与删除）；at 为下一步动作。
- **状态更新规则**：Σ_{t+1} = Σt ⊕ ΔΣt，其中 ⊕ 为带 null-删除语义的字典合并操作。
- **推理丢弃机制**：推理轨迹在状态转移被验证并应用后立即永久丢弃，不再出现在后续任何 prompt 中；推理投影为持久的结构化状态，从而让跨步骤的信息传递与历史长度无关。
- **复杂度保证**：
  - 传统对话式运行时：|Ct| = O(t)，累计复杂度 ∑|Ct| = O(T²)；
  - SKILL.state：|Pt| = O(|P| + |Σ| + |O|)，与执行步数 t 无关，累计复杂度为 O(T)。
- **算法流程**（伪代码核心）：
  ```
  for t = 0,...,T:
      接收最新观察 Ot
      构造 prompt (P, Σt, Ot)
      LLM 生成 (Rt, ΔΣt, at)
      确定性验证 ΔΣt
      Σt+1 ← Σt ⊕ ΔΣt
      执行动作 at
  ```

## 6. 主要结论与发现

- **精准性提升**：在长时程扩展中，T=200 时 SKILL.state 在 Warehouse 上准确率达 0.94，而 ReAct 跌至 0.74、Memory 为 0.84。
- **效率提升**：T=100 时比 Stateful 减少 16.2× token；T=200 时比 Memory 节省约 50× token。公共基准中 InterCode CTF 上 token 消耗降低 60.4%（vs. ReAct），τ-Bench Airline 上节省 40.5%。
- **鲁棒性提升**：在高噪声（50 事件/轮）下保持 0.98 的准确率，而 ReAct 从 0.68 跌至 0.53。
- **状态恢复优势**：面对外部环境漂移，历史型基线幻觉 5–14 步，SKILL.state 需 0 步恢复。
- **压制历史型方法的本质优势**：预算匹配实验中，Truncated、Summary-capped、LLMLingua 的准确率分别为 0.18、0.52、0.22，而 SKILL.state 为 0.94，说明结构化状态保留了统计压缩器无法保留的精确关系依赖。
- **小模型失败模式**：开源小模型（Gemma-4-31B 在 T=100）主要问题（68%）是状态更新时误删已有键，属于结构化输出依从性问题而非推理能力缺陷。

## 7. 优点与亮点

- **架构优雅**：用“显式状态”这一简单抽象同时解决提示词膨胀、上下文污染、历史重建负担三个问题，且是模型无关的通用运行时方案。
- **复杂度理论清晰**：给出严格的 O(1) 单步 prompt 上界和 O(T) 累计复杂度，贡献表述可验证、可复现。
- **中间推理保留机制**：步骤内多步推理保持完整，仅在验证后丢弃，兼顾了复杂推理能力与上下文精炼。
- **状态 schema 领域级复用**：一个 schema 覆盖整个 benchmark 的所有任务，降低了工程成本。
- **实验设计严谨**：预算匹配对照有效隔离变量，统计检验规范，模型/环境覆盖面广。

## 8. 不足与局限

- **充分统计量假设的限制**：SKILL.state 的稳健性取决于“执行状态可作为未来的充分统计量”这一前提。以下三类场景不成立：
  1. 动态环境中的 schema 未知，需在执行中在线发现；
  2. 早期观察的相关性在当时未被识别、因而未写入状态；
  3. 任务目标本身定义于历史轨迹之上（如审计、调试溯源、解释行为）。
- **实验覆盖不足**：未实验多智能体场景（并发写入的冲突解决语义仅提及未验证）；噪声研究仅覆盖无关性噪声；未包含更长上下文（>200 步）或更大规模任务集的压力测试。
- **小模型失效问题**：开源小模型因 JSON 依从性错误（漏键、类型不一致、语法错误）导致性能下降明显，说明该方案对模型的结构化输出能力有一定要求；论文仅将约束解码视为“未来工作”。
- **Schema 设计成本**：虽然每个领域只需设计一次 schema，但 schema 质量直接影响执行效果，论文未讨论如何系统化设计或自动生成 schema。
- **量化缺失**：未报告推理延迟（latency）的实际改善数据，仅报告 token 消耗；也未报告端到端运行时间的对比。
