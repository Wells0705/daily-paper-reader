## 摘要
大型语言模型（LLM）智能体调用外部工具以检索和推理超出预训练知识的信息。模型上下文协议（MCP）标准化了此类工具的呈现方式，而代理MCP服务器将众多后端服务器聚合到单个端点之后，为认证、策略执行和可观测性提供了安全且可管控的瓶颈点。该架构带来了两个相互叠加的挑战：一是上下文工程瓶颈，即在任何用户查询之前，完整的工具模式就使模型上下文窗口饱和；二是工具可发现性障碍，即用户和智能体无法在200多个MCP服务器中的2000多个索引工具中识别出最佳工具。提示缓存降低了重新处理成本，但既不能释放上下文容量，也不能提高准确性。我们提出了SCOUT（面向通用工具的选择性上下文优化），它将工具暴露重新定义为上下文选择问题，仅注入与当前步骤相关的工具。SCOUT呈现两个MCP元工具——tool_search和execute_tool，其中tool_search执行混合检索，通过倒数排名融合（Reciprocal Rank Fusion）将BM25稀疏匹配与稠密向量搜索相结合，返回前k个相关工具。借助零停机目录更新流水线，SCOUT同时解决了上下文饱和和工具发现挑战。在PayPal的生产环境中，SCOUT将MCP工具令牌消耗从140.2k个令牌（占上下文的70.1%）降至1.3k个令牌（占0.8%），减少了99%，在企业规模上降低了每次查询的推理成本。由于SCOUT以标准MCP工具的形式呈现，因此它与模型无关，且无需客户端修改。

## Abstract
Large language model (LLM) agents invoke external tools to retrieve and reason over information beyond pretrained knowledge. The Model Context Protocol (MCP) standardizes how such tools are surfaced, and a proxy MCP server aggregates many backend servers behind a single endpoint providing a secure, governable chokepoint for authentication, policy enforcement, and observability. This architecture creates two compounding challenges: a context-engineering bottleneck where full tool schemas saturate the model context window before any user query, and a tool discoverability barrier where users and agents cannot identify the best tool among 2,000+ indexed tools across 200+ MCP servers. Prompt caching reduces reprocessing cost but neither frees context capacity nor improves accuracy. We present SCOUT (Selective Context Optimization for Universal Tooling), which reframes tool exposure as a context-selection problem, injecting only tools relevant to the current step. SCOUT surfaces two MCP meta-tools -- tool_search and execute_tool -- where tool_search performs hybrid retrieval, fusing BM25 sparse matching with dense vector search via Reciprocal Rank Fusion to return the top-k relevant tools. Backed by zero-downtime catalog update pipelines, SCOUT resolves both context saturation and tool discovery challenges. In production at PayPal, SCOUT reduces MCP tool-token consumption from 140.2k tokens (70.1% of context) to 1.3k tokens (0.8%), a 99% reduction, cutting per-query inference cost at enterprise scale. Because SCOUT is surfaced as standard MCP tools, it is model-agnostic and requires no client-side modifications.

## 1. 核心问题与整体含义

- **研究背景**：LLM 智能体在企业环境中需调用外部工具获取实时信息并执行操作。Model Context Protocol（MCP）提供统一接口，而代理 MCP 服务器将 100+ 内部 MCP 服务器、2,000+ 工具聚合在单端点之后，实现集中的认证、策略执行与可观测性，构成企业 AI 工具访问的安全管控点。
- **核心问题**：该架构带来两个相互叠加的挑战：
  - **上下文工程瓶颈**：每个会话开始时全部工具 schema（在 PayPal 为 140,200 tokens，占 200k 上下文的 70.1%）即被注入，在用户消息之前便饱和上下文窗口，推高推理成本并降低工具选择准确率（"lost in the middle" 现象）。
  - **工具可发现性障碍**：200+ MCP 服务器、2,000+ 工具目录中，用户无法通过手工浏览确定正确服务器或工具；基础 MCP 协议不支持自然语言搜索。
- **既有方案的不足**：提示缓存只减少重复编码成本，无法释放上下文容量，模型每次前向传播仍关注全部目录，亦无法改善工具选择准确性。
- **整体含义**：需要从"更便宜地加载全部工具"转向"选择性地加载正确的工具"，将工具暴露重构为上下文选择问题。

## 2. 方法论

### 2.1 核心思想

- **SCOUT（Selective Context Optimization for Universal Tooling）** 将工具暴露重新定义为上下文选择问题，仅注入当前步骤相关的工具。
- 通过两个合成 MCP 元工具 **tool_search** 和 **execute_tool** 将"发现"与"执行"解耦，以标准 MCP 工具形式呈现，模型无关、无需客户端修改。

### 2.2 两阶段查询协议

1. **阶段一（发现）**：客户端调用 `tool_search`，传入自然语言查询（query）、top_k（默认 5，范围 [1,20]）和 scope（my_servers/all_servers）。代理执行混合检索，返回 top-k 相关工具的完整 schema（名称、服务器、描述、inputSchema）。
2. **阶段二（执行）**：LLM 检查返回的 schema 后调用 `execute_tool`，传入精确的 tool_name、server_name 和符合 inputSchema 的 arguments，代理将调用路由至对应上游 MCP 服务器。
3. **描述驱动编排**：tool_search 描述标注"REQUIRED FIRST STEP"并列举覆盖领域；execute_tool 描述标注"REQUIRED SECOND STEP"；两者领域类别重叠，保证任何查询检索到 tool_search 时 execute_tool 也在同批 top-k 中，避免二次查找。硬性护栏："Never guess a tool_name. Always get it from tool_search first."

### 2.3 混合检索核心流程

- **离线索引构建**：工具 schema → 结构化自然语言文档（工具名+服务器类别+服务器描述+工具描述+参数规格）→ OpenAI text-embedding-3-large 生成 3,072 维稠密向量 → 写入 Milvus（含 BM25 稀疏索引和 HNSW 稠密索引）。
- **在线查询**：双分支检索：
  - **稠密分支**：查询经 embedding 后，在 HNSW 索引上按余弦相似度取 top_k × 3 候选；
  - **稀疏分支**：原始查询文本直接对 BM25 稀疏索引检索，取 top_k × 3 候选；
  - **候选扩展**：每支分支取 3 倍候选，确保仅在一个分支中排名高、另一分支排名低的文档不被融合步骤遗漏；
  - **RRF 融合**：Milvus 原生 RRFRanker（k=60）融合两个排序列表，公式为：
    - `RRF_score(d) = Σ_r 1 / (k + rank_r(d))`（对 BM25 和稠密两个排序列表求和）
  - **降级策略**：OpenAI embedding 调用失败时自动退化为 BM25-only 稀疏检索；Milvus 索引不可用时回退到完整工具列表注入，保持 MCP 协议兼容。

### 2.4 索引生命周期管理

- Milvus 索引与服务器健康状态联动：服务器状态机为 PENDING → ACTIVE → DEGRADED → INACTIVE/REJECTED；ACTIVE 时工具入索引，DEGRADED/INACTIVE/REJECTED 时删除对应 chunks。
- 定时任务每 15 分钟轮询目录变更，通过三级缓存（内存 → Redis → MySQL）清除、重新拉取 schema 并重新注入。
- **插入-前-删除（insert-before-delete）upsert 策略**：先写入新向量再删除旧向量，实现零停机索引更新。
- 条件元工具注入：仅当客户端/代理在启用列表且索引已初始化时才暴露元工具，保证标准部署不受影响。

### 2.5 授权过滤与环境感知路由

- **范围过滤在检索层执行**：my_servers 模式将用户已映射服务器集合转换为 Milvus 元数据过滤表达式，在向量数据库内部完成权限边界执行，而非检索后过滤。
- **双连接器路由**：生产与开发连接器各暴露一对 tool_search/execute_tool，通过描述文本中的环境标识（"production" / "development"），LLM 依据自然语言意图（如"query production BigQuery"）即可选择正确环境的连接器，无需客户端配置。

## 7. 优点

- **元工具协议设计巧妙**：将工具发现作为一等 MCP 公民而非外部预处理层，通过描述文本驱动编排，模型无关、客户端无需任何修改，可组合于未来 MCP 扩展。
- **描述重叠的工程细节**：tool_search 与 execute_tool 共享领域类别标签，确保两个元工具在同一次检索中同时出现，消除额外查找开销。
- **混合检索领域适配**：通过结构化工具文档表示（名称+服务器上下文+参数语义）和 top_k×3 候选扩展 + RRF 融合，同时利用 BM25 的词汇精确性和稠密检索的语义泛化能力。
- **企业级工程完备性**：零停机索引更新、三级缓存、条件注入门控、检索层授权过滤、渐进式降级（稠密→BM25→全量注入）等设计，使系统在企业环境中可持续运行。
- **可观测性体系**：四层 Splunk 监控事件（会话量、RAG 分析、fallback 率、执行分析）为运维和容量规划提供数据基础。
- **环境感知路由**：通过自然语言意图而非手动切换实现生产/开发环境路由，降低用户认知负担。

## 8. 不足与局限

- **工具描述质量依赖**：MCP 服务器开发者编写的工具描述质量不一，差描述工具可能被系统性欠检索，系统无法自动检测或补偿。
- **无反馈学习闭环**：成功工具调用未用于改进嵌入或提升未来检索分数，缺乏长期自我优化机制。
- **索引同步延迟**：cron 每 15 分钟运行，schema 变更最多延迟 15 分钟才反映到索引；时间敏感的变更需手动强制刷新。
- **top_k 需手动调优**：无基于查询复杂度或置信度的自动校准机制，可能造成宽泛查询欠检索或窄查询浪费上下文。
- **评估覆盖有限**：49 条查询规模偏小，且缺乏与替代方案的量化对照实验；跨客户端验证仅报告"可用"，未报告不同客户端间的检索行为差异。
- **延迟目标未完全达标**：P95 936ms 高于设计需求中的 500ms 目标，长尾延迟来自冷缓存和高峰争用，可能影响代理交互流畅性。
- **安全边界需进一步验证**：检索层授权过滤依赖服务端映射关系准确性和 Milvus 过滤表达式实现的正确性，论文未报告权限绕过测试。
- **多环境路由依赖 LLM 理解**：环境选择完全依赖 LLM 对描述文本的理解能力，若 LLM 忽略环境标识可能误路由，且文中未报告此类错误的频率。
