## 摘要
LLM智能体日益承担长时运行的任务，其历史增长远超单个模型上下文窗口。现有方法将早期交互压缩或提取选定信息到固定记忆表示中，在未知未来需求之前就决定保留什么。我们提出Scroll，一个上下文管理器，将每个智能体会话视为一个可执行的会话环境。该环境由一个追加式事件日志和一个沙盒化的持久Python内核支撑。内核在模型调用间维护一个类型化命名空间，允许工具输出、检索到的历史以及派生状态绑定到变量，而不是在每次调用时序列化到提示中。模型编写的代码通过exec搜索、具体化并转换会话状态；仅显式打印的投影进入模型下一次调用的工作视图。因此，上下文管理成为一种编程任务，继承了LLM不断提升的编码能力，同时事件日志保留了无损的历史真值。当工作视图接近其预算时，过期的跨度被逐出但仍可恢复：一个逐出索引将紧凑的地标与精确的事件日志地址绑定，使智能体直接导航到被逐出的区域，而非搜索整个日志。以Qwen3.8-Max为骨干，Scroll在LongMemEval_S上达到94.8%；在BEAM_10M上达到73.1%，超过最佳已发布记忆系统5.1个百分点；在LOCA_256K上达到86.7%，超过最佳已发布长时程智能体37.4个百分点。

## Abstract
LLM agents increasingly take on long-running tasks whose history grows far beyond a single model context window. Existing approaches compress earlier interactions or extract selected information into fixed memory representations, committing to what to preserve before future needs are known. We present Scroll, a context manager that treats each agent session as an executable Session Environment. The environment is backed by an append-only Event Log and a sandboxed, persistent Python kernel. The kernel maintains a typed namespace across model calls, allowing tool outputs, retrieved history, and derived state to be bound to variables rather than serialized into the prompt at each call. Model-written code searches, materializes, and transforms session state through exec; only explicitly printed projections enter the model's working view for the next call. Context management thus becomes a programming task that inherits the improving coding abilities of LLMs, while the Event Log preserves lossless historical ground truth. As the working view approaches its budget, stale spans are evicted but remain recoverable: an eviction index keeps compact landmarks tied to exact Event Log addresses, so that the agent navigates directly to evicted regions instead of searching the full log. With Qwen3.8-Max as the backbone, Scroll achieves 94.8% on LongMemEval_S; 73.1% on BEAM_10M, surpassing the best published memory system by 5.1 points; and 86.7% on LOCA_256K, exceeding the best published long-horizon agent by 37.4 points.

## 论文总结：Context as an Environment: Programmatic Context Management for Long-Horizon Agents

### 1. 核心问题与整体含义（研究动机与背景）

LLM智能体正越来越广泛地被应用于长时程任务（如仓库级软件工程、开放网络深度研究等）。这类任务会生成跨越大量模型调用、工具执行、观测、失败与修正的较长轨迹。核心矛盾在于：

- **会话历史持续累积**，而每次模型调用的上下文窗口是有限的；
- **模型可有效利用的上下文远小于名义窗口**，长输入下的检索与推理能力随长度显著退化。

现有方案可归为两类，但存在共同的根本缺陷：

- **上下文压缩**：截断过期片段、丢弃工具输出、用摘要替换早期轨迹（CLAUDE Code、Codex CLI、Cursor等均采用此类机制），不可逆地丢失未被保留的细节；
- **外部记忆系统**：在摄入时通过事实抽取、摘要或知识图谱构建派生存储，检索时通过语义接口取回片段。其提取操作在写入时即已固定"什么值得保存、以何种形式保存、日后如何检索"，任何遗漏均不可恢复。

关键问题在于：**长时程任务往往需要精确的历史证据或对过去事件的非平凡计算（如比较相隔很远的工具输出），而相关信息与所需操作在观测时无法预知**——因此没有一个在观测时刻产生的摘要能保证满足未来的需求。

### 2. 提出的方法论

**核心思想**：将智能体的历史从模型上下文中剥离出来（context externalization），视为一个**可执行的会话环境（Session Environment）**。上下文管理不再是"序列化文本的压缩管理"，而是**编写程序**——模型通过代码自由地定位、具体化、计算会话状态，并自行决定将哪部分投影到下一次调用的工作视图中。

**系统架构——会话环境三组件**（对应状态 Sₜ = (Lₜ, Pₜ, Vₜ)）：

1. **追加式事件日志（Event Log，Lₜ）**——跨会话边界的持久化、纯追加的完整真值记录。每个事件获得不可变的单调递增 seq 地址，支持基于 BM25 的确定性全文检索（非嵌入向量，零索引时模型调用），以 SQLite 存储。
2. **持久化存储（Payloads，Pₜ）**——小载荷内联于 SQLite；大载荷外置到文件系统（JSON 或工件存储），事件行保留有界预览与恢复指针，通过惰性句柄（ToolResultRef、ArtifactRef）访问。
3. **持久运行时（Python Kernel，Vₜ）**——沙盒化 Python 内核跨模型调用存续，维护带类型、大小、来源元数据的命名空间。工具调用返回 Python 对象，驻留于内核供后续程序操作。每次调用前追加命名空间摘要（变量名、类型、形状）。

**程序化接口**（模型面对的记忆操作面）：

| 操作 | 接口 | 角色 |
|------|------|------|
| LOCATE | `ms.search(query, k, ...)` | BM25 排序全文检索 + 结构/种类/时间过滤，命中带 seq 地址 |
| MATERIALIZE | `ms.expand(seq)` / `ms.expand(lo, hi)` | 恢复精确轮次或序列区间，加载惰性句柄引用的大载荷内容 |
| COMPUTE | 普通 Python + 受许可的数据库/文件系统/工具接口 | 过滤、连接、聚合、解析更新、构造派生状态 |
| EXPOSE | `print(value)` | 将有界投影作为观测传入下一上下文，其余留在内核 |

**上下文管理流程**：模型每步编写 exec 程序（通过 repl exec 和 recall history python 两个工具执行），程序在事件日志与内核变量上操作；**只有显式 print 的输出跨过观测边界进入下一次模型上下文**。

**可恢复驱逐机制（Algorithm 1）**：当工作视图超过预算 ρC 时触发：

- 活动轮次、最近尾部、最新工具结果受保护；
- 按恢复代价升序驱逐：完整工具载荷先折叠为单个 seq 指针；
- 逐出跨度进入分层驱逐索引：**逐出内容不丢失**，仍以原样存于事件日志中；
- 索引采用**多层滚动压缩**：每层最多 k 块，满时保留最新完整细节，旧块各折叠为一行并入上层，占据 O(k logₖ n) 块，提供"近细远粗"的地址锚定地标（headline）；
- 恒定性不变量：**一切移出视图的内容保持可寻址**。

### 6. 主要结论与发现

1. **主结果**：Qwen3.8-Max 骨干下，Scroll 在 LongMemEval_S 上达 94.8%；BEAM_10M 上 73.1%，超过最佳已发布记忆系统（Exabase M-1，68.0）5.1 分；LOCA_256K 上 86.7%，超过最佳已发布长时程智能体（GPT-5.2-Medium + ReAct）37.4 分。
2. **LOCA 对比**：与同骨干的上下文管理策略基线相比，Scroll 在 128K/256K 上为 89.3/86.7，下降幅度最小（-2.6），而 Summarization/Retrieval Agent 下降超 21 点——表明绑定中间结果为环境对象而非携带原始文本能有效抵抗上下文增长造成的性能衰减。
3. **跨骨干**：所有骨干均能使用 Scroll，但能力越强收益越大——编码与查询规划能力强弱直接决定差距，35B 模型在 LOCA_256K 上骤降至 22.7。
4. **消融**：丢弃原始事件记录损失最重（BEAM_10M 从 73.1 降至 19.9）；移除持久内核损失 7.3 点；移除驱逐索引仅损失 1.8 点但集中在需跨片段拼接证据的任务类别。
5. **能力画像**：Scroll 在知识更新（92.5 vs. 最佳 75.0）、矛盾消解（88.1 vs. 最佳 58.8）等"需要原始证据顺序与出处"的类别上优势最大；在摘要生成（70.5 vs. 91.9）、偏好跟随、时间推理等"需先建浓缩视图"的任务上落后于最优摄入管线系统——失败源于查询表述而非系统不可恢复性。

### 7. 优点

- **核心洞察深刻**：将上下文管理重新定义为"每步在持久环境上选择工作视图的程序"，把选择从写入时刻推迟到查询时刻——这是对压缩/提取范式的范式性改进。
- **无损历史保证**：事件日志保留完整真值，驱逐只改变视图不改变记录，配合地址锚定索引导航，从机制上消除不可逆信息丢失。
- **发挥 LLM 编码优势**：上下文管理策略自然继承模型编程能力的进步，无需更改 harness 即可受益于更强骨干。
- **接口设计清晰**：LOCATE/MATERIALIZE/COMPUTE/EXPOSE 四操作将上下文构造分解为定位、具体化、计算、暴露四个正交步骤，简洁而完整。
- **成本效率显著**：BEAM_10M 中位输入仅约 105K token（约为语料库的 1%），摄入阶段零额外 LLM 调用，确定性 BM25 检索无需嵌入索引。
- **工程思想严谨**：小载荷内联/大载荷外置的存储分层、内核变量类型化与来源元数据、命名空间摘要等设计细节体现工程完备性。

### 8. 不足与局限

- **对比公平性受限**：与基线系统的对比并非受控实验——骨干模型、检索预算、评判器各异，结论仅具指示性；作者也承认此局限并因此未自行复现基线。
- **特定类别能力短板**：在摘要、偏好跟随、时间推理等需要摄入时构建浓缩视图的类别上，**不及**摄入型管线（如 Exabase M-1 摘要 91.9 vs. 70.5），失败模式为查询表述不精确（如偏好跟随示例中模型检索了工具偏好轴而非"避费"约束轴）。
- **对模型能力的强依赖**：跨骨干方差极大（LOCA_256K 上 86.7 vs. 22.7），弱模型无法编写足够复杂的查询规划程序，在实践中需要较强后端才能发挥系统优势。
- **多会话证据聚合仍有缺口**：LongMemEval_S→M 的降幅集中于多会话类型（88.0→81.2），轨迹分析显示失败源于过精确过滤导致低估证据集。
- **评估覆盖不完整**：单次运行无方差报告；消融仅限单一基准；未报告推理延迟、令牌级成本明细或与长上下文模型（如 1M 上下文模型）的直接对比。
- **算力信息缺失**：未提供任何训练/推理算力部署细节，影响可复现性与部署评估。
- **应用范围**：适用于可编程接口的智能体场景，对非代码型工具链或不支持 exec 的模型协议不适用。
