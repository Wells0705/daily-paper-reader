## 摘要
现代语言模型和智能体越来越需要持久记忆来存储完整的代码库、长时间交互历史以及异构企业记录。关键挑战在于，在仅向答案模型传递有限来源证据的同时，保持数亿个token的可搜索性。我们介绍了MegaMem，一个源解析的双视角检索系统，它将语义访问与生成证据分离。使用原始查询和转换查询搜索蒸馏记录和详细证据；每次蒸馏命中都会在倒数排名融合、去重和交叉编码器重排序之前解析为不可变的源ID；并且仅在固定预算内将排名最高的详细证据用于生成。回答后的归因然后识别哪些加载的源支持固定答案。我们在EnterpriseRAG-Bench上评估了MegaMem，该基准包含超过50万份异构企业文档和约6.5亿个token。MegaMem将Overall从68.22提高到82.26，并达到86.50的Correctness。这些结果表明，MegaMem支持超大规模持久记忆，同时在受限生成上下文中保持强大的答案准确性。通过将可搜索记忆规模与答案上下文大小分离，MegaMem为实现从数亿到十亿token的记忆上的准确检索提供了一条实用途径。我们的代码可在https://github.com/xfab-xinyuansong/MegaMem.git获取。

## Abstract
Modern language models and agents increasingly require persistent memory for complete codebases, long interaction histories, and heterogeneous enterprise records. The key challenge is to keep hundreds of millions of tokens searchable while passing only bounded source evidence to the answer model. We introduce MegaMem, a source-resolved dual-view retrieval system that separates semantic access from generation evidence. Distilled records and detailed evidence are searched with original and transformed queries; every distilled hit resolves to an immutable source ID before reciprocal-rank fusion, deduplication, and cross-encoder reranking; and only the highest-ranked detailed evidence within a fixed budget supports generation. Post-answer attribution then identifies which loaded sources support the fixed answer. We evaluate MegaMem on EnterpriseRAG-Bench, which contains more than 500,000 heterogeneous enterprise documents and approximately 650M tokens. MegaMem improves Overall from 68.22 to 82.26 and reaches 86.50 Correctness. These results show that MegaMem supports ultra-large persistent memory while preserving strong answer accuracy under a bounded generation context. By separating searchable memory scale from answer-context size, MegaMem provides a practical path toward accurate retrieval over memories ranging from hundreds of millions to one billion tokens. Our code is available at https://github.com/ xfab-xinyuansong/MegaMem.git.

## 2. 论文提出的方法论

### 核心思想
- **源解析双视图检索（source-resolved dual-view retrieval）**：将“语义访问”与“生成证据”分离。
  - **蒸馏视图（distilled view）**：存储紧凑的 typed memories，用于提升语义匹配和检索召回；
  - **详细视图（detailed view）**：保留原始证据块及其来源元数据，用于最终生成。
- 所有蒸馏命中必须解析回对应的**不可变详细源块（源 ID）**之后，才能进入融合、重排和生成阶段。这样压缩记忆仅作为检索入口，而非独立证据。

### 关键技术细节
1. **双视图记忆构建（Dual-View Memory Construction）**
   - 文档规范化后按标题、段落边界切分为 **section-aware evidence chunks**；
   - 对每个 chunk，用 `gpt-5.4-mini` 提取最多三条 typed memories：`(τ, u, v, π)`，其中 `π` 指向源 chunk ID；
   - 五类记忆：事实（fact）、过程（procedure）、定义（definition）、要求（requirement）、决策（decision）；
   - 分别构建详细索引（原始 chunk 嵌入）和蒸馏索引（typed memory 嵌入），二者共享相同底层源。

2. **多路检索与证据解析（Multi-Route Retrieval and Evidence Resolution）**
   - 对问题 q 构造多个查询路由：原始查询、规范改写、术语多样性扩展等；
   - 每个路由同时检索详细索引 `I_d` 和蒸馏索引 `I_m`；
   - 蒸馏命中通过 `π(m)` 映射到详细 chunk；
   - 候选集定义为：
     \[
     C(q) = \bigcup_{r \in Q(q)} \left( \text{Retr}(r, I_d) \cup \pi(\text{Retr}(r, I_m)) \right)
     \]
   - 使用加权倒数排名融合（RRF）合并不同路由的排名（`γ=60`）；
   - 交叉编码器对融合后的候选重排，按源身份去重，直到填满证据预算 B。

3. **有界生成与回答后归因（Bounded Generation & Post-Answer Attribution）**
   - 生成仅使用详细证据：\( a = A(q, E(q)) \)，蒸馏记忆或未选中的源不进入生成；
   - 回答固定后，独立归因模块 `Z = C(a, E(q))` 识别支持回答的文档，**只能从报告集中移除源，而不能修改答案或引入新证据**；
   - 这一顺序明确区分了：查询扩展提升召回 → 重排选择证据 → 归因降低报告源数量。

### 算法流程（文字说明）
- **构建阶段（Algorithm 2）**：对每个详细 chunk，加入详细索引；对每个蒸馏记忆，加入蒸馏索引并记录源 ID。
- **推理阶段（Algorithm 1）**：生成查询路由 → 双索引检索 → 蒸馏解析 → RRF 融合 → 重排去重 → 打包至预算 B → 返回证据集。
- **归因阶段（Algorithm 3）**：基于证据生成答案 → 归因模块筛选支持源 → 交集确保不报告未加载文档。

## 6. 论文的主要结论与发现

1. **端到端质量大幅提升**：
   - 400 问验证集上，MegaMem 将 Overall 从已发布 leader 的 68.22 提升至 **82.26**，Correctness 达 **86.50**，Completeness 达 **86.98**，Document Recall 达 **81.90**。
2. **双视图+蒸馏贡献最大**：
   - 移除双索引使 Overall 下降 **17.91%**；
   - 移除蒸馏使 Overall 下降 **14.15%**；
   - 说明“语义访问与生成证据分离”是核心设计。
3. **可扩展性**：
   - 从 20M 到 250M token，Correctness 保持在 73% 以上，Overall 缓慢下降（71.67→58.02），未出现崩溃；
   - 生成证据预算始终有界，证明可搜索记忆规模与生成上下文可以解耦。
4. **检索 vs 生成瓶颈**：
   - 金证据情况下，Correctness 变化很小（20M→250M 仅 −0.30%/−2.33%），而检索证据下下降 12.50%/19.93%；
   - 结论：规模扩展的性能损失主要来自**检索**，而不是答案模型的生成/利用能力。
5. **回答后归因的作用**：
   - 归因不改变答案质量，但将平均报告文档数从 **5.00 降至 2.31**，InvDocs 从 0.774 降至 0.760。
6. **证据效率**：
   - MegaMem 使用详细证据但**选择性打包**，相比“全详细证据”，输入 token 减少约 **69%**，Correctness 仅损失约 1.5 分；
   - 蒸馏-only 证据非常短但 Correctness 极低（21/17），证明蒸馏只适合检索、不适合生成。
7. **转移能力有限**：
   - FinanceBench（Overall 81.05）和 HotpotQA（86.37）表现好；
   - LoCoMo（42.34）和 UltraDomain（17.73）较差，说明文档导向的记忆表示在跨会话、跨域大规模共享场景下仍有不足。
8. **查询扩展与可答性权衡**：
   - 在可回答问题类别上带来 20.8%–100% 的相对增益；
   - 但在“信息不存在”问题上，无条件扩展会将 Correctness 从 100% 降至 68.8%，需引入可答性门控。

---

## 7. 优点

- **问题定义清晰且实际**：明确区分 persistent context 与 evidence context，并形式化约束（有界证据预算），指向真实部署需求。
- **架构设计有洞察**：将压缩记忆仅用作检索键、强制解析到源证据，避免了“压缩失真污染答案”的问题；检索与生成职责分离具有通用指导意义。
- **诊断方法严谨**：
  - 金证据干预能可靠区分 retrieval failure 与 generation failure；
  - 逐步架构开发（Table 9）展示了从压缩记忆到双视图的演进逻辑。
- **评估维度全面**：不仅报告答案质量，还覆盖文档召回、无效引用率、token 开销、时延、离线构建成本。
- **消融实验完整**：leave-one-component-out 清楚地量化了各组件贡献。
- **可复现性考虑**：提供代码、固定 seed 42、温度 0、API 超时与重试策略、以及完整 prompt 模板（附录 J）。

## 8. 不足与局限

- **实验统计性薄弱**：大多数结果为单次运行，缺乏多次运行方差/置信区间，结论稳定性存疑。
- **部分结果来自估计而非独立运行**：详细证据-only 对照组的 token 数据基于保留轨迹估计，可能引入偏差。
- **源精度仍低于已发布 leader**：MegaMem 的 InvDocs（0.760）明显高于也已发布的 leader（0.470），说明归因后仍会报告较多无效文档，在“引用精确性”上仍有明显差距。
- **跨任务迁移有限**：在 LoCoMo 和 UltraDomain 上表现很差，说明方法主要适用于文档级、证据单元边界清晰的企业语料，对会话式、跨域动态共享记忆场景不通用。
- **扩展性实证上限**：主结果最高只做到 250M token，尽管标题称“ultra-large context”并声称支持至 1B token，但并没有真正在 1B 规模上实验。
- **生成模型与评估依赖 API**：使用 GPT-5.4 系列与 OpenAI embedding，存在商业模型版本漂移与不可复现风险；同时没有自有开源模型下的验证。
- **没有提供对比模型的细节**：Baselines（如 DPR、Contriever）的实现方式、调参或训练细节未充分说明，可能影响公平性。
- **未扩展原生注意力窗口**：MegaMem 只是增加了可搜索语料的规模，并没有改变底层模型的实际上下文长度上限，对于需要全局跨 chunk 推理的问题（如 UltraDomain 所示）仍会受限。
